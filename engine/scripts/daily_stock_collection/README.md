# X4 금융위원회 일봉 수집 (n8n)

**Python 직접 수집:** 신규 API 3종 수집기는 [PYTHON.md](PYTHON.md) 참고. 아래는 기존 n8n 도구의 보존 문서다.

운영 중인 `My workflow 2`의 2026-10-15 설정을 공유용으로 내보냈다. LLM·제품 런타임과 독립된 수집 PC용 운영 도구다. 서버 DB에 추가하며 앱의 분석 기준일·지수·종목 마스터·Parquet은 바꾸지 않는다.

## 가져오기와 실행

1. n8n의 **새 워크플로**에서 `workflow.json`을 가져온다. 기존 운영 워크플로에 추가로 가져오면 노드·일정이 중복될 수 있다.
2. `금융위 일봉 전체 페이지1`에서 Query Auth Credential을 선택한다. 이름은 `serviceKey`, 값은 승인된 API 인증키다. 키를 노드 코드·URL에 직접 적지 않는다. URL 인코딩된 키는 한 번 디코딩한 값으로 등록해 이중 인코딩을 피한다.
3. `DB 기존 자료 확인`, `일봉 3개 테이블 저장` 두 노드에 서버 담당이 준비한 같은 MySQL Credential을 선택한다. 인증값은 저장소에 넣지 않는다. 수집 PC의 SELECT/INSERT 전용 계정을 쓴다.
4. 세 테이블은 서버에 이미 있어야 한다. MariaDB의 `JSON_TABLE`과 트랜잭션을 지원하는 저장 엔진을 전제로 한다. 이 워크플로는 DDL·권한 부여를 하지 않는다.
5. 처음에는 `전체 건수와 일봉 검증1`의 Execute step으로 API 응답만 확인한다. 이후 전체 수동 실행으로 DB 저장 결과를 확인한다.
6. 시간대 `Asia/Seoul`, 트리거 `0 30 13 * * *`(매일 13:30)를 확인하고 Publish/활성화한다. 가져온 파일은 **비활성 상태**이며 기존 워크플로와 동시에 예약하지 않는다.

API 인증키·DB 주소·비밀번호는 내보내지 않았다. 각 환경에서 Credential을 연결해야 한다. n8n과 DB 서버가 켜져 있고 네트워크가 연결되어야 예약 실행된다. 실패 알림은 운영 환경의 Error Workflow로 별도 설정한다.

## 수집·저장 범위

- 기본 조회는 KST 어제까지 최근 7일이다. 초기 적재는 `조회 기간 설정1`의 beginDate/endDate를 실제 YYYYMMDD로 함께 지정하며 한 번에 최대 31일이다. 초기 적재 후 두 값을 빈 문자열로 되돌린다.
- 모든 페이지의 건수·순서·중복을 확인한 뒤 KOSPI/KOSDAQ만 선택한다. KONEX는 저장하지 않는다. 날짜·OHLC·정수 범위를 검증하며 큰 정수는 문자열로 유지한다.
- `store_prices`, `store_krx_daily`, `store_marketcap`에 신규 행만 INSERT한다. 같은 키·같은 값은 건너뛰고 기존 값 충돌은 쓰기 전에 중단한다. UPDATE/DELETE/REPLACE는 없다.
- 세 테이블 쓰기는 n8n MySQL 노드의 `queryBatching=transaction`으로 묶는다. 실패 무시/다음 단계 계속 실행을 켜지 않는다. 동시 실행은 피하고 충돌하면 전체 상태를 확인한 뒤 재시도한다.
- 결정 X4a에 따라 2026-09-18 이후 `prices`는 기업행사가 없다는 가정으로 원주가를 쓴다. `dept`는 2026-09-18 값을 잇고 기준 종목이 없으면 NULL이다. 과거 날짜를 덮어쓰지 않으며 정확한 수정주가 정정은 X4b 후속 과제다.
- `DB 저장 결과`는 쓰기 노드 성공 후에만 출력된다. 준비 노드의 report는 예상 건수이므로 저장 성공 증거로 사용하지 않는다.

## 조회 종료일과 실제 최신일은 다르다

`endDate`는 요청 범위이고 `latestDate`는 응답에 실제 존재하는 가장 늦은 기준일이다. `latestMatchesRequestedEnd=false`이면 종료일까지 모두 반영됐다고 표시하면 안 된다. 휴장일 또는 제공기관 지연일 수 있어 원인을 구분해야 한다. 없는 날짜를 0건 정상 완료나 임의 시세로 채우지 않는다.

2026-10-15 16:36 KST 확인: 10-08~10-14 요청의 API 응답 9페이지/8,609행 중 KOSPI·KOSDAQ 8,288행, 실제 최신일 10-13이었다. DB 세 테이블도 10-13 2,761행으로 일치했다. 10-14 자료는 응답에 없었다. 이는 그 시각의 관측 기록이며 고정 갱신 지연일을 의미하지 않는다. 다음 예약에서도 최근 7일을 다시 조회한다. 지연이 7일을 넘으면 빠진 기간을 수동으로 나눠 재수집해야 한다.

## 검증

```powershell
node engine/scripts/daily_stock_collection/checks.cjs
uv run --project engine python -m pytest engine/tests/test_daily_stock_workflow.py
```

합성 테스트는 워크플로에 내장된 코드를 직접 실행한다. 페이지 누락·중복·업무 오류·잘못된 날짜/OHLC·큰 정수·KONEX 제외·13:30 일정·최근 7일·요청일과 반환일 차이·파라미터 바인딩·중복 적재·기존값 충돌·과거 보호를 확인한다. API/DB에 접속하지 않는다.

운영 검증 기록: 초기 2026-09-21~10-13의 13일분 35,930행을 세 테이블 각각 적재했고, 이후 최근 구간 8,288행 재실행에서 신규 0·동일값 8,288행을 확인했다. 다른 PC·DB 버전의 실제 트랜잭션 실패 복구는 이 합성 검사로 입증되지 않는다.
