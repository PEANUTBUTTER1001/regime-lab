## 1. 범위와 운영 전제

Supabase Auth를 사용하여 이메일·비밀번호 회원가입, 이메일 인증, 로그인, 로그아웃, 비밀번호 재설정을 제공한다. 웹은 기존 정적 ES 모듈과 FastAPI를 사용한다.

일반 사용자는 본인이 만든 백테스트, 역방향 탐색, 저장한 조합만 조회·취소·수정·삭제할 수 있다. 인증은 계정 확인, 인가는 각 자원의 소유자 확인으로 구분한다. API 전체에서 확인하므로 브라우저의 `signedIn` 값을 바꿔도 권한이 생기지 않는다.

첫 운영 형태는 FastAPI 한 프로세스·분석 작업 한 개이다. 다른 사용자 작업 때문에 busy이면 그 작업의 ID나 상세 상태를 응답하지 않는다. 외부 공개 도메인·HTTPS·호스팅과 메일 발송 서비스는 X3.3에서 확정하고, 그 전 검증은 loopback에서 한다.

현재 로컬 데모는 명시적인 인증 비활성 모드에서만 제공한다. 비활성 모드는 loopback으로 제한한다. 실사용 인증 모드에서는 게스트가 사용자 기록이나 유료 모델 호출·분석 실행에 접근하지 않으며, 로그인 화면의 데모 진입은 공개된 안내 범위로 제한한다.

2026-10-12 사용자 요청으로 Google·카카오 회원가입과 로그인을 추가한다. 기존 이메일·비밀번호 방식도 유지한다.

## 2. 데이터와 인증 흐름

| 데이터 | 보관 위치·처리 |
|---|---|
| 이메일·비밀번호 해시·이메일 인증 상태 | Supabase Auth의 PostgreSQL. 앱은 비밀번호 원문을 저장하지 않는다 |
| 로그인 세션 | 서버 메모리. 서버가 만든 무작위 세션 ID의 해시를 키로 사용자 ID와 Supabase access/refresh token을 보관 |
| 브라우저 인증 | 서버가 발급한 불투명 세션 ID를 HttpOnly 쿠키로 전달. 자바스크립트·localStorage·sessionStorage에는 인증 토큰을 저장하지 않는다 |
| 실행·탐색·조합 소유자 | 서버 전용 SQLite 인덱스. 자원 종류·자원 ID·Supabase 사용자 ID만 저장. 계정 DB나 시장 데이터 DB와 별개 |
| 조합 ID | 기존 ID 형식은 유지하고 인증 모드에서 사용자 namespace를 ID 생성 입력에 포함하여 같은 이름·시각의 사용자 간 충돌 방지 |
| 조합 파일 | 인증 모드에서 사용자 ID별 하위 폴더에 저장하여 이름 충돌·조회 범위도 분리 |
| 분석 산출물 | 기존 실행·탐색·조합 저장소. 응답 JSON과 계산 의미는 소유자 인덱스와 분리 |
| 공개용 연결 키 | FastAPI 프로세스 환경변수. 소스·문서·로그·응답에 실제 값 없음 |

세션 ID는 충분한 난수로 생성하고 로그인 때 교체한다. 쿠키는 `HttpOnly`, `SameSite=Lax`, `Path=/`를 사용하고 HTTPS 운영에서는 `Secure`를 강제한다. HTTP 쿠키는 명시적인 loopback 개발에만 허용한다.

서버는 Supabase가 확인한 사용자 ID로 세션을 생성한다. 보호 API는 서버 세션 확인 및 Supabase 세션 유효성 확인 후 호출한다. access token 만료 시 refresh token을 갱신하고, 갱신 결과의 사용자 ID가 원래 세션과 같은지도 확인한다. 로그아웃은 서버 세션을 즉시 제거하고 쿠키를 지우며 Supabase refresh 세션도 해제한다.

서버 재시작 시 메모리 세션은 사라져 재로그인이 필요하다. 소유자 인덱스는 유지된다. 여러 서버·worker에 세션을 공유하는 배포는 이 첫 버전의 운영 전제가 아니므로 별도 저장·암호화 설계가 필요하다.

소유자 인덱스는 `REGIME_AUTH_STATE_DIR`로 지정한 서버 전용 위치에 둔다. 새 결과의 소유자 기록에 실패하면 성공 응답을 내지 않고 접근을 차단한다. 소유자를 기록하지 않은 과거·CLI 결과는 일반 사용자에게 노출하지 않는다. 별도 소유자 이관 승인 없이 기존 자료를 사용자에게 자동 귀속하지 않는다.

## 3. 공개 API 변경안

인증 응답에는 사용자 ID·이메일·인증 상태만 포함한다. 비밀번호, API 키, Supabase access/refresh token은 JSON 응답에 포함하지 않는다. 오류 형식은 기존 `{code, message, detail, retryable}`를 사용한다.

| 메서드·경로 | 요청·응답 |
|---|---|
| GET `/api/auth/config` | 공개 설정: 인증 사용 여부와 지원 로그인 방식. 키 값 제외 |
| POST `/api/auth/signup` | `{email,password}` → 202 이메일 확인 안내. 계정 존재 여부를 드러내는 응답을 피함 |
| GET `/api/auth/confirm` | 이메일 확인용 token hash 검증 후 고정된 앱 로그인 화면으로 이동 |
| POST `/api/auth/login` | `{email,password}` → 200 사용자 정보, 서버 세션 쿠키 발급 |
| GET `/api/auth/me` | 유효한 세션 → 사용자 정보. 유효하지 않으면 401 |
| POST `/api/auth/logout` | 세션 제거·쿠키 삭제 → 204 |
| POST `/api/auth/recover` | `{email}` → 202 재설정 안내. 계정 존재 여부에 따른 차이 없음 |
| GET `/api/auth/recovery/confirm` | Supabase 복구 token hash 확인 후 제한된 비밀번호 재설정 세션 발급 |
| POST `/api/auth/password` | 복구 세션과 `{password}` 확인 → 변경 후 앱 세션 제거, 재로그인 안내 |

일반 변경 API는 인증 모드에서 미로그인 401이다. 다른 사용자 자원과 존재하지 않는 자원은 같은 404 응답으로 처리한다. 목록은 본인 자원만 반환한다. 일반 사용자의 공용 LLM 설정 변경은 403으로 제한하고, 기존 loopback 설정 변경 제한도 유지한다. 운영 시 모델 사용 한도와 공용 키 비용 책임은 배포 전 확정한다.

쿠키를 사용하는 POST/PUT/DELETE 요청은 허용된 정확한 Origin과 CSRF 증명을 확인한다. 인증 전 로그인·가입·복구 요청도 Origin 검사를 받는다. 같은 서버에서 발급한 CSRF 증명은 자바스크립트가 헤더로 보낼 수 있지만 인증 세션의 비밀 값과 구분한다. callback의 목적지는 서버 설정으로 정하며 임의 redirect URL을 받지 않는다.

메일 확인·복구 링크의 token hash를 검증한 뒤 쿼리 없는 URL로 이동한다. 해당 값이 access log·오류·응답·Referer에 남지 않도록 필터와 `no-store`·`no-referrer`를 적용한다. 복구 세션은 비밀번호 변경 경로에만 쓸 수 있고 일반 분석 API에는 쓸 수 없다.

## 4. 책임·의존성과 승인 대상 경로

| 역할 | 추가·변경 위치 | 책임 |
|---|---|---|
| 진입 | `api/src/regime_api/routes/auth.py`, 기존 라우트·`schemas.py` | 입력 검증, 유스케이스 호출, 쿠키·응답 변환 |
| 유스케이스 | `api/src/regime_api/auth/service.py` | 가입·로그인·복구 흐름, 세션·권한 판단, 소유자 확인 |
| 포트 | `api/src/regime_api/auth/contracts.py` | Supabase 호출·세션/소유자 저장 협력자의 계약과 값 타입 |
| 인프라 | `api/src/regime_api/auth/supabase.py` | 고정된 Supabase URL로 HTTPS 호출, 민감 값 제거·공급사 오류 변환 |
| 인프라 | `api/src/regime_api/auth/store.py` | 메모리 세션·SQLite 소유자 인덱스, 동시 접근 제어 |
| 인프라 | 기존 `api/src/regime_api/settings.py` | 환경변수 검증, callback 로그 필터 설정 |
| 조립 | 기존 `api/src/regime_api/main.py` | 시계·난수·공급사·저장소 생성과 DI, 보호 경계·라우터 연결 |
| 기존 유스케이스 | `api/src/regime_api/jobs.py` 등 | 자원 생성과 소유자 저장 실패 시 성공 응답 방지·다른 작업 ID 숨김 |
| 웹 | 기존 로그인·앱·API·상태·문구 사전, `web/js/views/password.js` | 실제 API 연결, 서버 상태 확인, 재설정 화면·한국어/영어 문구 |
| 설정 | `engine/config/default.yaml`에 auth 절 추가 | 인증 수치 기준. 기존 확정 분석 파라미터 변경 없음 |
| 테스트 | `api/tests/test_auth_contract.py`, `api/tests/test_auth_ownership.py` | 원본·실제 계정·실제 키 없는 인증·권한 계약 검증 |

`auth/` 패키지는 기존 LLM 유스케이스와 같은 수준에 둔다. 유스케이스 위에 추가 서비스 계층을 만들지 않는다. `auth/__init__.py`는 패키지 진입만 맡는다.

의존은 진입 → 유스케이스 → 포트이며, Supabase·SQLite 구현은 포트를 구현하고 조립에서만 생성한다. 포트는 실제 HTTP·DB 없이 만료·공급사 장애·소유자 저장 실패를 재현하는 테스트 대역 때문에 필요하다. 웹은 기존 `api.js`만 호출한다. 엔진은 계정·Supabase·웹을 import하지 않는다.

외부 서비스 Supabase는 사용자 선택을 전제로 한다. 새 SDK 대신 REST 호출을 사용한다. HTTP 대역 테스트에 이미 쓰는 `httpx`를 API의 직접 런타임 의존성으로 추가 선언하는 것을 제안한다. Supabase SDK·Next.js·번들러는 추가하지 않는다.

초기 수치 제안: 세션 최대 8시간, 비활동 30분, 복구 세션 10분, HTTP timeout 10초. 로그인 실패 횟수·가입/복구 발송 한도는 Supabase 제한과 앱 제한을 함께 검토하고 설정 파일에서 관리한다. 구현 전에 수치도 확정한다.

서버 환경변수:

- `REGIME_AUTH_MODE`: `supabase` 또는 loopback 전용 `demo`
- `REGIME_SUPABASE_URL`
- `REGIME_SUPABASE_PUBLISHABLE_KEY`
- `REGIME_AUTH_SITE_URL`: loopback 개발 주소 또는 HTTPS 운영 주소
- `REGIME_AUTH_STATE_DIR`: 소유자 인덱스 위치
- `REGIME_AUTH_ADMIN_IDS`: 관리자 Supabase 사용자 ID 허용 목록

제공받은 실제 키·DB 비밀번호는 문서나 예제에 기록하지 않는다. 환경변수가 누락됐을 때 인증이 자동으로 해제되는 폴백을 만들지 않는다.

## 5. 검증과 출시 기준

1. 유효·잘못된 비밀번호·이메일 미확인·Supabase 장애·불완전 설정을 실제 키 없이 검증한다.
2. 미로그인 API, 세션 만료·교체·갱신, 로그아웃 후 이전 쿠키 재사용을 검증한다.
3. 사용자 A/B의 실행·탐색 목록·결과·상태·취소·보고서와 조합 CRUD가 분리되는지 검증한다.
4. 소유자 없는 과거 기록, 소유자 저장 장애, 다른 사용자 작업으로 busy인 상황에서 접근·정보 노출이 없는지 검증한다.
5. 다른 Origin·CSRF 증명 누락·임의 callback 목적지·복구 세션의 일반 API 사용을 차단한다.
6. 응답·설정·로그·브라우저 저장소에 키·비밀번호·인증 토큰이 남지 않는지 검증한다.
7. 기존 engine·api·ingest 테스트를 실행하고 분석 수치·결과 JSON 의미를 보존한다. 테스트 임시 폴더는 루트 `cache/` 아래에 둔다.
8. 한국어/영어 로그인·오류·재설정 화면, 새로고침 후 로그인 유지, 가입·이메일 확인·로그아웃을 브라우저에서 확인한다.

Supabase 기본 메일 발송은 개발 확인용 제한이 있으므로 외부 사용자 가입·복구를 운영하기 전에 커스텀 SMTP와 발신 도메인을 확정한다. 확인/복구 메일 템플릿·callback 허용 URL은 코드의 실제 경로와 함께 적용한다.

현재 실행 중인 사용자 서버는 별도 재시작 승인 없이 중단하지 않는다. 검증은 별도 포트의 sample 서버로 진행할 수 있다. 실제 이메일 발송·계정 생성은 사용자가 직접 입력하는 테스트 계정으로 확인한다.

이 문서 승인 후 새 모듈·환경변수·의존성 경로를 `/agents-md` 개정 요청에 포함한다. AGENTS.md를 직접 개정하지 않는다.

## 7. feat/X3-supabase-auth 구현 상태와 실행 안내 (2026-10-12)

코드: Supabase 이메일·비밀번호 인증, 서버 메모리 세션, HttpOnly 쿠키, CSRF/Origin 검증, 사용자별 실행·탐색·저장 조합 접근 제한을 구현했다. 기존 서버를 중단하거나 develop에 합치지 않았다. 세션은 단일 서버 프로세스에서 유지되며 재시작하면 다시 로그인한다. 소유자 인덱스와 사용자별 조합 폴더는 서버를 재시작해도 보존해야 한다. 소유자가 없는 과거 기록은 인증 모드에서 공개하지 않는다.

### Supabase 메일 설정

Site URL은 `http://127.0.0.1:8000`이며, 아래 두 Redirect URL은 저장을 확인했다.

- `http://127.0.0.1:8000/api/auth/confirm`
- `http://127.0.0.1:8000/api/auth/recovery/confirm`

Resend 테스트 SMTP 연결과 아래 확인·복구 템플릿 저장을 확인했다. SMTP 인증은 성공했지만 실제 이메일 발송·계정 생성·복구는 아직 검증하지 않았다. 테스트 발신 도메인은 Resend에 등록된 본인 주소에만 발송할 수 있으므로, 외부 사용자를 위한 발신 도메인은 운영 전에 별도 연결해야 한다.

Confirm sign up:

```html
<a href="{{ .SiteURL }}/api/auth/confirm?token_hash={{ .TokenHash }}">Confirm email address</a>
```

Reset password:

```html
<a href="{{ .SiteURL }}/api/auth/recovery/confirm?token_hash={{ .TokenHash }}">Reset password</a>
```

기본 템플릿은 Supabase에서 이메일을 확인한 뒤 브라우저 fragment로 토큰을 넘긴다. 이 구현은 fragment 토큰을 가져오거나 저장하지 않는다. 기본 템플릿으로 확인이 끝난 계정은 이메일/비밀번호로 직접 로그인할 수 있지만, 앱의 확인 완료 안내와 복구 세션 발급은 위 템플릿 설정을 필요로 한다. HTTPS 배포 시 Site URL·환경변수·Redirect URL을 실제 도메인으로 함께 바꾼다.

## 8. Google·카카오 가입/로그인 (2026-10-12)

동일한 버튼으로 처음에는 Supabase 계정을 생성하고 이후에는 로그인한다. 이메일/비밀번호 가입도 유지한다. 사용자가 요청한 두 공급사만 허용하며 새 SDK·라이브러리·모듈을 추가하지 않는다.

- `POST /api/auth/oauth`: `{provider:"google"|"kakao"}`. Origin/CSRF·로그인 시도 한도를 확인하고 고정된 Supabase authorize URL을 반환한다. 공개 설정에는 `social_providers` 활성 여부만 추가한다.
- `GET /api/auth/oauth/callback`: HttpOnly `rl_oauth` 쿠키로 연결된 서버 메모리의 PKCE verifier로 code를 교환한다. 흐름은 5분 동안 한 번만 사용할 수 있으며 새 시도·로그아웃·서버 재시작은 이전 흐름을 무효화한다. 실패하면 기존 세션을 유지하고 고정 로그인 화면으로 돌아간다.
- verifier와 Supabase access/refresh token은 서버 메모리에만 둔다. 쿠키에는 불투명 흐름 ID만 넣고 callback query는 access log·Referer에서 제거한다. Supabase가 반환한 사용자 ID와 identities의 선택 공급사를 확인한 뒤 기존 세션/소유자 정책을 적용한다.
- 소셜 계정에 이메일이 없는 경우에도 확인된 소셜 identity로 인증할 수 있다. 이메일 확인이 없는 소셜 사용자의 이메일/비밀번호 로그인은 기존처럼 차단한다. 계정 연결/이메일로 사용자 ID 병합은 앱에서 수행하지 않는다.
- 활성 여부 조회가 실패하면 소셜 버튼을 비활성화하며 이메일 방식은 유지한다. 활성 공급사가 없으면 준비 중 문구를 표시한다.
