## 1. 작업 개요

- 작성일: 2026-10-15 KST.
- 작업: X12·X12.1·X12.2. 구현 담당 PEANUTBUTTER1001, 리뷰어 hongsungmin0315.
- 목적: 데이터 서버 PC의 데모 앱에 지정 팀원 PC만 접속하도록 허용하고, 기존 로컬 데모·Supabase 인증·LLM 설정 제한 보존.

- 요청 근거: 사용자 “1a / 2b /3b 공통기본안 반영 3개의 사항은 문서로 기록할것 이제 구현전 검토후 $srs”. 문서 기록은 명시 요청에 따라 수행, 코드 구현은 명세 승인 후 수행.

- 데모 모드용 REGIME_ALLOWED_NETS 환경변수·Settings 필드·시작 검증.

## 3. 기능 요구사항

| ID | 요구사항 |
|---|---|
| FR1 | 기존 인증 모드 결정 방식을 유지하고, 확정된 모드를 기준으로 LAN 설정 처리 여부 결정 |
| FR2 | 데모 모드에서 허용 목록을 쉼표로 분리·공백 제거 후 IPv4 네트워크로 해석. IPv4 단일 주소는 /32로 처리, 빈 항목은 제외. 잘못된 비어 있지 않은 항목 하나라도 있으면 시작 거부 |
| FR3 | 허용 네트워크 전체가 D2의 RFC1918 범위 하나에 포함돼야 함. is_private 단독 판정·잘못된 CIDR의 자동 범위 확장 금지. 환경변수뿐 아니라 직접 생성한 Settings의 같은 필드도 검증 |
| FR4 | 데모 바인딩이 비 loopback이면 비어 있지 않은 허용 목록 필수. 0.0.0.0은 수신 바인딩으로 허용하되 허용 목록의 0.0.0.0/0은 거부. 기존 localhost·loopback 기본 실행 유지 |
| FR5 | 데모 모드에서 허용 목록이 설정된 경우 모든 HTTP 경로·메서드에 필터 적용. /api·정적 파일·OpenAPI·없는 경로·OPTIONS 포함. 요청자의 실제 연결 주소를 먼저 검사하고 목록 밖이면 후속 처리 이전에 차단 |
| FR6 | 요청자 IP는 request.client.host로 판정, 전달 헤더를 직접 읽어 신뢰하지 않음. 데모 모드의 공식 regime-api 진입점은 Uvicorn proxy_headers=False 적용. Supabase 실행 옵션·인증 경로는 기존 유지 |
| FR7 | loopback은 자동 허용. IPv4-mapped IPv6는 내장 IPv4로 정규화 후 같은 규칙 적용. native IPv6 원격·접속자 정보 없음·IP로 해석 불가한 값은 활성 필터에서 거부. ::1과 IPv4 loopback의 mapped 표현은 로컬로 허용 |
| FR8 | 차단 시 403과 errors.body의 code=network_not_allowed·고정 message·detail=null·retryable=false를 직접 JSONResponse로 반환. 입력된 목록·원격 주소·비밀값을 오류 본문에 포함하지 않음 |
| FR9 | Supabase 모드는 D3대로 LAN 설정 무시. 환경변수의 형식 오류·IPv6·공인 대역 값도 파싱하지 않으며 직접 전달한 LAN 필드로 요청 필터를 활성화하지 않음 |
| FR10 | 허용된 원격 데모 요청도 LLM PUT·DELETE는 기존 local_only 403. GET의 기존 응답·Supabase 관리자 조건 보존. LLM 코드 공통화·새 모듈 분리 없이 경계 사례로 동작 보존 확인 |
| FR11 | 데모 실행·탐색의 기존 IP별 요청자 구분 유지. 다른 IP는 대기열 공유, 같은 IP의 중복 요청 제한 유지. 요청자 판정·대기열 구현 수정 제외 |
| FR12 | 실제 운영의 앱 허용 목록과 방화벽 범위를 팀원별 /32 정책에 맞춤. 서버 PC 수용 확인에서 실제 접속·차단·LLM 제한·X13 대기→완료를 기록한 뒤에만 X12 전체 완료 판정 |

## 4. 입력·출력 및 인터페이스

| 항목 | 명세 |
|---|---|
| 설정 입력 | REGIME_AUTH_MODE·REGIME_HOST·REGIME_PORT는 기존 규칙. 신규 REGIME_ALLOWED_NETS는 데모 모드 전용, 기본 미설정 |
| Settings 필드 | allowed_nets, 기본 빈 목록. 데모 검증을 통과한 IPv4Network 목록. Supabase에서 효과 없음 |
| 문법 | 쉼표 구분 IPv4/CIDR. 단일 IP는 /32. CIDR은 strict 검증, host bits가 있으면 거부 |
| 수신 주소 | 실제 서버 운영은 IPv4 바인딩. 0.0.0.0은 허용 목록의 주소가 아닌 수신 주소 |
| 성공 출력 | 기존 라우트 응답·웹 파일·인증 계약 유지 |
| 차단 출력 | HTTP 403·application/json·{code, message, detail, retryable}, code=network_not_allowed |
| 시작 실패 | ValueError 등 기존 설정 검증 방식. 고정 메시지에 설정 이름·잘못된 항목 위치 정도만 표시, 실제 주소/원문 값 미포함 |
| 공개 계약 영향 | 데모 모드 시작 조건의 선택적 완화, 신규 환경변수·403 오류 코드 추가. 기존 API 경로·요청/응답 스키마·CLI 인자·저장 형식 변경 없음 |

## 5. 예외 및 경계 상황

- 미설정·빈 문자열·공백·쉼표만 있는 값: 빈 목록. 비 loopback 데모는 시작 거부, 기존 loopback 데모는 정상.
- 유효·무효 항목 혼합: 데모 시작 거부. 무효 항목만 조용히 제거하는 처리 제외.
- 공인·특수·link-local·native IPv6 네트워크·전체 대역: 데모 허용 목록에서 거부. loopback은 목록에 넣을 필요 없이 자동 허용.
- IPv4-mapped 주소를 목록에 쓰는 입력은 IPv6 입력으로 거부하되 실제 접속자의 mapped 표현은 IPv4로 정규화.
- 실제 같은 망의 범위·팀원 신원은 RFC1918 판정만으로 증명되지 않음. 운영 /32 명단·서버 방화벽으로 통제.
- 로컬 프록시·터널은 loopback 자동 허용과 결합하면 원격 접속자를 로컬로 오인할 수 있음. 이번 운영에서 사용 제외, proxy_headers=False만으로 이를 해결했다고 주장하지 않음.
- Supabase 자체 필수 설정이 잘못되면 기존대로 시작 거부. LAN 변수 무시는 Supabase 자체 검증 생략을 뜻하지 않음.
- 방화벽이 먼저 차단한 접속은 HTTP 403 대신 연결 실패 가능. 앱 필터와 방화벽 수용 검증을 구분.

## 6. 비기능 요구사항 및 제약

- 설정·환경변수 접근은 settings.py, 필터 생성·연결은 main.py. 엔진·도메인 계산 변화 없음.
- 표준 라이브러리 ipaddress와 기존 FastAPI/Starlette 사용. 새 라이브러리·서비스·아키텍처 예외 추가 없음.
- 원본·regime.duckdb·외부 자료·뉴스 수신·LLM 호출 불필요. 검사 입력은 합성·대역 표준 예시만 사용.
- 웹 파일·화면 문구 변경 없음. Python 3.12 및 기존 빌드 없는 웹 구조 유지.
- 실제 IP·서버 주소·키는 공개 저장소에 기록하지 않음. 저장소 밖 배포 문서 원문을 복사·커밋하지 않음.
- 기존 문서 6개의 미커밋 변경 보존. WBS 갱신 시 대상 행만 변경, BOM·CRLF·비대상 행 바이트 보존.

## 7. 가정 및 확인 필요 사항

### 가정

- D1은 실제 운영의 허용 목록 정책. B22의 기존 CIDR 입력 기능은 유지하며 /32만 받는 파서로 축소하지 않음. /24 지원과 /24 운영 기본 채택은 구분.
- 운영 주소는 IPv4. native IPv6 원격 접속이 필요한 경우 별도 후속 범위.
- 공식 실행 경로는 uv run --project api regime-api. 다른 ASGI 실행기·프록시 환경의 전달 주소 처리까지 보장하지 않음.
- loopback 전용·허용 목록 미설정 시 기존과 같이 별도 요청 필터 없음. 실제 네트워크 접속 제한은 loopback 바인딩으로 유지.

### 확인 필요

- 정책·명세 승인 완료. 정책 1A·2B·3B·공통 기본안 재선택 필요x. 실제 서버 환경 확인은 아래 별도 단계.
- 서버 적용 직전: Seonghwanaa와 팀원 주소 고정·환경변수·실제 실행기·프록시 부재·방화벽 확인. 현재 코드 구현의 선행 입력 아님.
- 실행 중 사용자 서버 재시작은 해당 작업 직전 별도 승인 대상. 이번 명세 승인으로 실제 서버 조작을 일괄 승인한 것으로 취급하지 않음.

## 10. 검증 계획

- 구현 승인 후 API 기준선 → 새 원본 없는 정책 검사 → 기존 인증·소유자·로그인 화면·LLM·대기열 관련 검사 → 전체 회귀 순서.
- 신규 검사는 원본 의존 conftest의 base_paths/sample_prep/client fixture를 사용하지 않음. 임시 Paths·준비 상태 대역·외부 호출 없는 인증 대역 사용.
- 실행 진입점 검사로 Uvicorn 인자 확인. 실제 전달 헤더 처리 검증은 격리된 별도 포트·합성 상태의 Uvicorn에서 허용/거부 주소를 제어해 수행. TestClient 결과만으로 Uvicorn 옵션 효과를 입증하지 않음.
- 전체 명령: uv run --project engine python -m pytest engine / uv run --project api python -m pytest api / uv run --project ingest python -m pytest ingest. 기존 환경 사용 시 --no-sync 가능.
- Windows 임시 경로는 짧은 루트 cache/<실행별 이름>, pytest cache_dir도 루트 cache 아래. 기존 권한 문제 패키지 cache는 필요 시 수집 제외하고 그 사실 기록.
- 문서 검사는 git diff --check·상대 링크·상태 표기·보존 해시 대조. 실행 결과는 아래 구현 상태 및 progress/PROGRESS.md에 기록.
- 실제 서버 수용 전까지 AC12는 미확인 유지. 기존 회귀·문서 보고 수치를 현재 새 코드의 검증값으로 인용하지 않음.
