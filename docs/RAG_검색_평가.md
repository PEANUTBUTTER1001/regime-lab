## 1. 해결하려는 문제

- 과거 시점(as_of)의 브리핑·분석이 그때 알 수 없었던 문서를 근거로 쓰면 미래 정보 누설이다.
- 누설 경로는 두 가지다. ① 보이는 문서 ② BM25 의 IDF·평균 길이 같은 **말뭉치 통계**. 문서만 시점으로 걸러도 통계를 전체 문서로 내면 미래 문서가 늘 때 과거 순위가 바뀐다(n8n 엑셀 실측: 10-01 23:59 기준 "증권사 실적" 4·5위가 뒤바뀜).
- 그래서 역색인은 한 번만 만들고, 통계는 질의마다 as_of 에 보이는 문서로만 계산한다. `engine/tests/test_rag_rank.py` 가 절단 불변(미래 문서 50건 추가)과 대조군(전체 통계면 점수가 바뀜)을 함께 검사한다.

## 2. 검색 규칙

| 단계 | 규칙 |
|---|---|
| 문서 | `<ext_store>/docs/source=*/date=*/part-*.parquet` 확정본만. manifest `schema_version` 1 이 아니면 거부 |
| 시점 | `observed`(기본): `first_seen_at ≤ as_of` 그리고 `available_at ≤ as_of`. `historical_assumed`: `available_at ≤ as_of`. `doc_id` 별 최신 버전, `status == "deleted"` 는 늘 제외 ([`P3_수집_계약.md`](P3_수집_계약.md) §4) |
| 색인 필드 | 설정 `rag.index_fields` = 제목·회사명 (제품). 요약 등은 CLI `--fields` 개인 실험에서만 |
| 토큰화 | NFKC·영문 소문자 정규화. 한글 연속 구간은 문자 2-gram, ASCII 영숫자 연속 구간은 식별자 그대로. 혼합 문자열에서 숫자 일부를 자르지 않음 |
| 순위 | BM25(k1·b 는 설정), 동점은 `doc_id` 순. 보이는 문서로 점수 통계를 계산한 뒤 완전 조건 미충족 문서를 제외하고 후보 제한·묶기/MMR 적용. 완전 조건은 검색어 단위 원형 또는 허용 조사 변형으로 검사하며, 조사 목록·기본어 최소 길이는 설정. MMR 은 `rag.mmr_lambda` 가 null 이면 끔 |
| 비슷한 제목 묶기 | `rag.group_threshold`(잠정 0.3)가 있으면 BM25 상위 `rag.group_candidate_k`(100)개를 순위 순서로 훑어, 앞 묶음 대표와 **질의 글자를 뺀** 제목 자카드가 문턱 이상이면 그 묶음에 넣는다. 결과는 묶음 대표, 나머지는 `similar`. 묶음은 그 시점에 보이는 후보로만 만든다(미리 전체 문서로 묶으면 미래 기사가 과거 묶음을 바꿈, `test_grouping_is_cut_invariant`). 글자 겹침이라 '같은 사건' 판정이 아니며 화면도 '제목이 비슷한 기사'로 쓴다. 묶기를 켜면 MMR 은 쓰지 않는다 |
| 근거 없음 | 보이는 문서 0건, 질의 토큰 불일치, 모든 질의 조건을 충족한 후보 없음(구분자뿐인 질의 포함), 상위 점수 ≤ `rag.min_score` → `no_evidence` |
| 캐시 | 루트 `cache/rag/index_<키>.json`, 키 = `INDEX_VERSION` + `rag` 설정 + 문서 지문 |

`observed` 모드에서 소급 공시는 실제로 처음 본 날 이전 시점에 보이지 않는다. 과거 일봉 연구는 `historical_assumed` 로 따로 조회하고 결과를 분리해 보고한다.

## 3. API 계약 (P3-13 화면용)

`GET /api/evidence/search`

| 쿼리 | 필수 | 값 |
|---|---|---|
| `q` | 예 | 1~200자 |
| `as_of` | 예 | 시간대 포함 ISO 8601 (예 `2026-10-07T15:30:00+09:00`) |
| `mode` | 아니오 | `observed`(기본) · `historical_assumed` |
| `tickers` | 아니오 | 6자리 종목코드 쉼표 구분 |
| `k` | 아니오 | 1~20, 기본 5 |

응답 200: `{status, items, index, disclaimer}`

| 필드 | 뜻 |
|---|---|
| `status` | `ok` · `no_evidence` (근거 없음도 200) |
| `items[]` | `doc_id`, `version`, `source`, `title`, `corp_name`, `url`(원출처), `published_at`, `time_precision`(`date_only` 면 화면에 "날짜만"), `first_seen_at`, `available_at`, `score`, `matched_tokens`(검색 근거), `similar_count`, `similar[]`(`doc_id`·`title`·`source`·`url`·`published_at`·`time_precision`·`available_at`) |
| `index` | `index_version`, `docs_fingerprint`, `fields`, `total_docs`, `visible_docs`, `mode`, `as_of`, `grouping`(묶기 문턱, 끄면 null) |
| `disclaimer` | 비권유 고지 |

오류(공통 형식 `{code, message, detail, retryable}`): 422 `validation_failed`(`detail.fields`), 503 `warming_up`(재시도 가능), 503 `data_unavailable`(ext_store 없음·문서 없음·스키마 불일치, 빈 결과로 대신하지 않음).

## 4. 평가 기준

평가셋과 실험 데이터는 **저장소 밖**에 둔다(외부 자료 원문 포함, AGENTS.md §7). 형식만 여기 적는다.

```text
[{id, query, type, as_of, mode?, tickers?, split: "dev"|"test",
  relevant: [{url | doc_id, grade?}], clusters?: {url|doc_id: 사건ID}}]
```

- 규모·분할: 40~60문항, 7개 유형(종목명·약칭·다른 표현·같은 사건·시점·답 없음·전제 오류). 튜닝은 `dev` 만, `test` 는 마지막에 한 번 `--split test` 로 채점한다.
- 정답 후보는 여러 방식의 상위 결과와 직접 찾은 결과를 합친 뒤 표시한다(BM25 쪽으로 기울지 않게). 10문항은 팀원 1명이 따로 표시해 일치율을 기록한다.
- 묶기를 켜면 묶음 하나가 순위 하나다. 정답 기사가 대표가 아니라 `similar` 안에 있어도 그 순위에서 찾은 것으로 센다.
- 지표: Recall@5, MRR, nDCG@5, 고유 사건 수@5, 근거 없음 정확도(답 없는 질문의 근거 없음 비율 / 답 있는 질문의 잘못된 근거 없음 비율), 질의 p50·p95 지연.

```bash
uv run --project engine regime-lab rag-eval --gold <저장소 밖 평가셋.json> --split dev --docs <문서 폴더>
```

- 묶기·MMR 없이 상위 20건이 모두 한 사건("자사주 계획 물량 매입 완료")의 다른 언론사 기사였다.
- MMR(제목 자카드, λ 0.5·0.3)은 순서만 바꾸고 상위 10건이 여전히 같은 사건이었다 — 후보 20건이 모두 같은 사건이라 고를 다른 사건이 없음. 그래서 MMR 대신 묶기를 택했다.
- 묶기 문턱: 질의 글자를 포함하면 결과가 질의 글자를 공유해 27건이 한 묶음이 됐다(문턱 0.3). 질의 글자를 빼면 0.2 는 '대한제강 주가 상승'과 '대한전선 주가 하락' 같은 틀 제목을 잘못 묶어, 다른 근거를 가리지 않도록 보수적으로 0.3 을 잠정값으로 뒀다.
- 0.3 결과: 상위 10개 묶음 안에 비슷한 기사 13건이 접혔다(7·4·2건). 같은 사건이지만 표현이 달라 따로 남은 기사도 있다(예 '100% 돌파', '목표량 다 사들였다'). 문턱은 평가셋의 사건 표시(`clusters`)와 고유 사건 수@5 로 조정한다.

채택·제외한 기술과 이유는 측정 뒤 이 절에 적는다.

| 중복 정답 식별자 | 같은 문서가 URL·doc_id로 중복될 때 마지막 등급이 덮어쓰던 구조 | 동일 문서는 최고 양수 등급으로 통합, 입력 순서 무관. 작성 단계에서는 중복 제거 권장 |
| 평가셋 오류 | 구조·중복 ID·잘못된 분할·0문항을 검증하지 않거나 내장 예외 유출 | 선택 분할 전체를 검색 전에 검증, validation_failed. CLI 파일 누락·잘못된 JSON·인코딩도 종료 코드 2로 처리 |

검색 선택·순위·토큰화·API·CLI 인자·저장 형식 변경 없음. `INDEX_VERSION=2` 유지. 평가기의 입력 검증·비관련 자료 처리만 변경하므로 기존 평가 수치와 비교할 때 이 변경 여부 기록 필요.

## 7. 실데이터 평가 준비·실행 절차

### 7.1 평가셋 작성 규칙

- §4 JSON 형식 유지. 전체는 배열, 문항은 객체이며 고유한 비어 있지 않은 문자열 `id`와 `split: dev|test` 필수.
- 선택 분할의 `query`·시간대 포함 `as_of`·`relevant` 필수. `relevant: []`는 답 없음. `mode` 기본 observed, `type` 생략 시 untyped, `tickers`는 문자열 배열.
- 정답의 `url` 또는 `doc_id`는 비어 있지 않은 문자열. `grade` 기본 1, 0은 비관련, 양수는 관련도. 음수·문자열·불리언·NaN·무한대·DCG 이득이 유한하게 계산되지 않는 등급은 거절.
- `clusters`는 자료 식별자 → 사람이 검토한 사건 ID의 문자열 객체. 검색의 제목 유사도 묶음을 실제 사건 정답으로 복사하지 않는다.
- dev 실행에서는 다른 분할의 ID·분할 표기만 검사하며 test 정답은 채점·검증하지 않는다. test 실행 때 해당 정답 검증. 선택 분할 0문항은 정상 평가가 아닌 오류.
- 문항 정답은 해당 as_of·mode·종목 조건에서 이용 가능해야 한다. 파일에 존재하지만 그 시점에 보이지 않는 정답은 자동 교정하지 않으므로 작성자가 시점을 검토한다.
- 같은 문서를 URL/doc_id로 중복 표기하지 않는다. 잘못된 URL·다른 문서에 공유된 URL을 피하고 가능한 경우 doc_id 사용. 현 형식은 정답을 문서 단위로 표시하며 버전별 관련도를 표현하지 않음; 버전 정확성은 별도 합성 테스트로 검증.

합성 형식 예시(실제 평가 문항·성능 증거 아님):

```json
[
  {"id":"dev-01","query":"한빛반도체 자기주식","type":"종목명","as_of":"2026-10-07T18:00:00+09:00","mode":"observed","split":"dev","relevant":[{"doc_id":"opendart:20261007000000","grade":1}]},
  {"id":"test-01","query":"없는회사","type":"답 없음","as_of":"2026-10-07T18:00:00+09:00","split":"test","relevant":[]}
]
```

### 7.2 실행 순서

1. 서버에서 허용된 자료 스냅샷·manifest·문서 지문 확보. 실제 자료와 평가셋은 저장소 밖에 보관. 현재 PC로 원본을 복사하지 않음(F1d).
2. 40~60문항을 §4의 7개 유형으로 구성하고 dev/test 분리. 직접 찾은 후보와 여러 검색 방식의 후보를 함께 검토. 10문항은 별도 검토자와 독립 표시 후 일치율 기록(자동 메시지 전송 없음).
3. dev만 채점하여 질문·정답 오류와 검색 품질 확인. 데이터·설정·지문·문항별 결과·경고·지연 기록. 정답 누락 경고는 원인을 검토하며 임의 삭제로 지표를 높이지 않음.
4. 구성·정답 고정 후 test를 명시적으로 1회 평가. CLI는 명시 요청 여부만 확인하며 과거 실행 횟수를 잠그지는 않음. 재평가가 필요하면 사유를 기록하고 최종 평가셋 재사용 한계를 표시.
5. 결과를 §5에 측정값으로 기록. 합성 테스트의 1.0 점수를 실제 검색 품질로 기재하지 않음. 삭제·만료 미확정 사항도 평가 한계에 포함.

```powershell
uv run --project engine regime-lab rag-eval --gold '<저장소 밖 평가셋.json>' --split dev --docs '<서버 ext_store>'
```

구성 고정 후에만:

```powershell
uv run --project engine regime-lab rag-eval --gold '<저장소 밖 평가셋.json>' --split test --docs '<서버 ext_store>'
```

CLI stdout에는 색인 요약 한 줄 다음 평가 JSON 출력. 전체 출력을 곧바로 JSON 파일로 파싱하지 않고 요약 줄과 분리한다. 실패는 stderr의 오류 코드·필드와 종료 코드 2 확인. 새 출력 옵션·파일 형식은 추가하지 않음.

### 7.3 결과 해석·완료 구분

| 결과 | 해석 |
|---|---|
| `overall`·`by_type` | 양수 정답이 있는 문항의 평균. recall은 상위 k 묶음의 모든 정답 포함 여부, MRR·nDCG는 기존의 묶음별 첫 양수 정답 대표 방식. nDCG의 이상적 순서는 문서별 등급 기준이라 여러 정답이 한 묶음에 있으면 완벽한 문서 회수여도 1 미만 가능 |
| `abstention` | 답 없는 문항의 근거 없음 비율, 답 있는 문항의 잘못된 근거 없음 비율. 해당 종류가 없으면 null, 0%로 해석 금지 |
| `unique_clusters` | 사람이 표시한 사건 기준. 미표시 자료는 각자 다른 사건으로 계산하므로 라벨 범위 함께 기록 |
| `latency_ms` | 질의 p50·p95. 색인 구축·초기 입력 검증 시간은 제외. 서버·자료 규모 함께 기록 |
| `warnings` | 문서에 없는 양수 정답. 경고를 없애려고 정답을 제거하지 않고 입력 누락·식별자 오류를 확인 |
| 이번 작업 완료 | 합성 검증·평가 입력/채점 수정·실행 절차 준비 |
| P3-11 전체 완료 잔여 | 삭제·만료 계약, 실데이터 40~60문항 측정, 정답 10문항 독립 검토 |
| 2026-10-20 갱신 | 사용자가 서버 PC에서 위 잔여를 직접 확인·통과했다고 보고하여 WBS P3-11을 완료 처리. 측정값·평가셋·삭제·만료 계약 문서는 저장소에 없고, develop 코드에 삭제·만료 처리가 없음 |

## 9. 조사 변형·완전 조건 검색 — 2026-10-15 승인 구현

§8은 당시 웹 보고·인수인계 기록으로 보존. 이후 현행 엔진·로컬 시연 자료로 세 오류를 직접 재현하고, 사용자가 조사 지원 SRS에 `$execute` 호출. 약칭·별칭 작업은 사용자 요청으로 제외. 명세·수용 기준은 [검색 품질 개선 명세](RAG_검색_품질_개선_명세_20261015.md) 참조.

### 9.1 확정한 검색 규칙

- 각 질의 단위는 원형 또는 허용 조사 변형 전체를 같은 문서의 제목·회사명에서 확인. 모든 단위를 충족해야 반환하며 부분 글자 일치로 완화하지 않음.
- 기본 조사는 `이/가·은/는·을/를·과/와`. 받침 규칙에 맞을 때 1회만 분리하고, 기본어 최소 2글자·문서의 독립 단어 경계 확인. 목록과 최소 길이는 `rag.query_particles`·`rag.particle_min_base_chars`로 관리.
- `삼성전자가→삼성전자`, `대한전선은→대한전선`, `SK하이닉스가→SK하이닉스`는 공통 규칙으로 처리. 종목명 하드코딩 없음. `국가→국`, `전문가→전문`, `대한전선→한전`은 불허.
- NFKC·소문자 정규화 뒤 점수용 한글 2-gram과 ASCII 영숫자 식별자 분리. `ZXQ987`은 통째로 두며 `98`을 생성하지 않음. 기존 `2분기` 점수 토큰은 이제 `2`·`분기`.
- BM25 통계는 시점·명시 종목 필터에서 보이는 집합 유지. 점수가 있는 행에 완전 조건 검사를 수행한 뒤 후보 수 제한·묶기/MMR 적용. 대표와 similar에 동일한 자격 적용.
- INDEX_VERSION=3. API·CLI 인자·응답 형식·수집 스키마·웹은 유지. matched_tokens는 실제 점수 기여 토큰이며 의미 분석 결과 아님.
