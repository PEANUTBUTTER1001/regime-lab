## 2. 브랜치

- 공식 원본은 `develop`이다. `develop`에 직접 푸시하지 않는다(관리자도 원칙적으로 PR을 쓴다).
- 작업마다 `develop`에서 새 브랜치를 만든다. 이름은 `<종류>/<WBS ID>-<짧은 영문 설명>`이다.
  - 종류: `feat`(기능), `fix`(결함), `docs`(문서), `test`(테스트), `chore`(설정·도구)
  - 예: `feat/P1-5-candidate-generator`, `fix/M3-report-units`, `docs/G1-srs-v2`
  - WBS ID가 없는 작업은 ID 없이 `<종류>/<설명>`으로 쓴다.
- `main`은 현재 쓰지 않는다. 발표 버전 표시 방식은 P4-9(릴리스 정리)에서 정한다.

## 3. 커밋과 PR

1. 커밋 메시지는 Conventional Commit 형식(`feat: …`, `fix: …`, `docs: …`)을 쓴다(결정 C4). 설명은 한국어로 써도 된다.
2. PR은 `develop`으로 보낸다. 제목도 같은 형식으로 쓴다.
3. PR 본문에 다음을 적는다.
   - WBS ID와 변경 요약
   - **로컬 테스트 결과**(E14): 아래 두 명령의 결과 줄(통과·skip 수)을 붙인다

     ```bash
     uv run --project engine python -m pytest engine
     ```

     ```bash
     uv run --project api python -m pytest api
     ```

   - 화면을 바꿨으면 화면 캡처와 한국어·영어 확인 여부
   - 공용 파일(§4)이나 버전 상수(§5)를 바꿨는지
4. 리뷰어 1명의 승인을 받은 뒤 **squash 병합**한다. 병합 후 브랜치는 자동으로 지워지지 않으므로, 필요 없으면 작성자가 직접 지운다.
5. 리뷰어는 바뀐 파일의 주인(§4)을 우선 지정하고, 주인이 본인이면 관련 작업 담당자를 지정한다.

## 5. 버전 상수

다음 상수는 올리는 순간 다른 사람의 캐시·결과가 무효가 되므로 **올리기 전에 팀에 알린다.**

| 상수 | 올리는 때 | 영향 |
|---|---|---|
| `PREP_VERSION` (`engine/src/regime_lab/pipeline.py`) | 지표·유니버스·국면·워밍업·패턴 계산을 바꿀 때 | 준비 캐시와 기존 실행의 종목 상세(`409 stale_run`) |
| `PROMPT_VERSION` (`api/src/regime_api/llm/prompt.py`) | LLM 프롬프트·근거 수치를 바꿀 때 | 보고서 캐시 |

- PR 제목이나 본문에 "PREP_VERSION 3으로 올림"처럼 표시한다.
- 두 PR이 같은 상수를 올렸다면 늦게 병합하는 쪽이 한 번 더 올린다.
- 일정상 캐시를 무효로 만드는 작업(X4·X5·X6·P1-4)은 M4 회귀 전에 끝내고, P4-9(통합 회귀) 시작 뒤에는 코드를 바꾸지 않는다(코드 동결).

## 6. 커밋하면 안 되는 것

저장소는 **공개**다. 한 번 올라간 내용은 지워도 기록과 사본이 남을 수 있다.

- 원본 데이터: `data/`, `multi_tables_db/`, 1분봉 원본, 외부 자료 원문
- 실행 결과·캐시: `runs/`, `cache/`
- 비밀: API 키·토큰, `.env*`, `engine/config/paths.local.yaml`
- 개인정보: 이메일·전화번호 등. 팀원 실명은 문서에 쓰지 않고 GitHub 아이디로만 지목한다. 계정·역할 기준은 이 문서 §1과 SRS §8에 둔다

## 7. 자동 검사 (CI)

- F2 이후 PR마다 원본 데이터 없이 engine·api 테스트를 자동 실행한다(E14). 데이터가 필요한 테스트는 skip되고 skip 수가 표시된다.
- 자동 검사가 통과해도 데이터가 필요한 테스트는 돌지 않은 것이다. 그래서 §3의 로컬 테스트 결과 첨부는 CI가 생긴 뒤에도 계속 필수다.
