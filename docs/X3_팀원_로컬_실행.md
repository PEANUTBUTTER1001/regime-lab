# 다른 PC에서 로그인 실행하기 (X3)

각 팀원이 자기 PC에 저장소를 받고 로컬 웹 서버를 실행하는 방법이다. 작성자의 PC 접속이나 별도 복사본 서버가 필요하지 않다. 소셜 로그인은 팀의 Supabase 프로젝트를 공통으로 사용하고, 로그인할 때는 각자의 Google·카카오 계정을 사용한다.

## 1. 준비할 것

- Git, uv, Python 3.12 실행 환경과 인터넷 연결.
- `hchee99`에게 전달받은 **Supabase 프로젝트 URL**과 **publishable 공개 키**. 새 Supabase 프로젝트나 개발자 앱을 각자 만들 필요는 없다.
- 로그인 테스트에는 DB 비밀번호, Google/Kakao Client Secret, Supabase service-role 키, Resend 키가 필요하지 않다. 공급사 비밀키는 공통 Supabase 관리 설정에만 둔다.

## 2. 코드 받기

처음 받는 PC에서만 실행한다. 저장할 폴더 위치는 자유다.

```bash
git clone https://github.com/PEANUTBUTTER1001/regime-lab.git
cd regime-lab
```

기존 저장소가 있으면 그 저장소 루트로 이동한다. 아래는 **PR #71 병합 여부에 따라 하나만** 선택한다. 작업 중인 변경이 있으면 별도 폴더에 clone해서 테스트한다.

PR #71 병합 전:

```bash
git fetch origin
git switch feat/X3-social-auth
git pull --ff-only origin feat/X3-social-auth
```

PR #71 병합 후:

```bash
git fetch origin
git switch develop
git pull --ff-only origin develop
```

선택한 브랜치에서 설치한다.

```bash
uv sync --project engine
uv sync --project api
```

로그인만 확인할 때 시세 SQL 덤프 추출·백테스트 준비·n8n 실행은 필요하지 않다. 자료가 없는 분석 화면의 `Data unavailable`은 로그인 실패와 별개다.

## 3. 각 PC에서 설정하고 실행하기

아래 URL·공개 키 자리표시자 두 개를 전달받은 실제 값으로 바꾼다. `REGIME_AUTH_STATE_DIR`은 각 PC의 사용자 폴더에 자동으로 잡으며 다른 사람의 폴더를 복사하지 않는다. 관리자 UUID는 일반 로그인 테스트에 필요 없어 빈 값이다. 환경변수를 입력한 **같은 터미널**에서 서버를 실행한다.

Windows PowerShell:

```powershell
$env:REGIME_AUTH_MODE = "supabase"
$env:REGIME_SUPABASE_URL = "https://<프로젝트>.supabase.co"
$env:REGIME_SUPABASE_PUBLISHABLE_KEY = "<sb_publishable_공개키>"
$env:REGIME_HOST = "127.0.0.1"
$env:REGIME_PORT = "8000"
$env:REGIME_AUTH_SITE_URL = "http://127.0.0.1:8000"
$env:REGIME_AUTH_STATE_DIR = Join-Path $env:LOCALAPPDATA "regime-lab/auth-state"
$env:REGIME_AUTH_ADMIN_IDS = ""
uv run --project api regime-api
```

macOS/Linux (bash/zsh):

```bash
export REGIME_AUTH_MODE="supabase"
export REGIME_SUPABASE_URL="https://<프로젝트>.supabase.co"
export REGIME_SUPABASE_PUBLISHABLE_KEY="<sb_publishable_공개키>"
export REGIME_HOST="127.0.0.1"
export REGIME_PORT="8000"
export REGIME_AUTH_SITE_URL="http://127.0.0.1:8000"
export REGIME_AUTH_STATE_DIR="$HOME/.local/share/regime-lab/auth-state"
export REGIME_AUTH_ADMIN_IDS=""
uv run --project api regime-api
```

브라우저에서 **http://127.0.0.1:8000/#/login**을 연다. PC가 달라도 각자 이 주소를 쓰면 된다. `localhost`, 다른 포트, 다른 PC의 IP로 임의 변경하면 앱의 Origin 검사 또는 OAuth 복귀 주소와 맞지 않을 수 있다. 기본 예시는 8000이며 작성자 PC에서 사용했던 8001은 필수 포트가 아니다.

8000이 이미 사용 중이면 기존 작업을 확인한 뒤, 다른 포트를 쓸 경우 `REGIME_PORT`, `REGIME_AUTH_SITE_URL`, 아래 Supabase 허용 callback의 포트를 모두 맞춘다. 이미 실행 중인 서버는 환경변수 변경을 자동으로 읽지 않으므로 그 서버 운영자가 재시작해야 한다.

## 4. 프로젝트 관리자가 공통으로 확인할 설정

같은 프로젝트·같은 로컬 주소를 쓰는 팀원마다 다시 설정할 필요는 없다.

| 위치 | 설정 |
|---|---|
| Supabase Auth Providers | Google·Kakao 활성화 및 해당 개발자 Client ID/Secret 설정 |
| Supabase Redirect URLs | `http://127.0.0.1:8000/api/auth/oauth/callback` 허용 |
| Google·Kakao 개발자 콘솔 | Supabase callback `https://<프로젝트>.supabase.co/auth/v1/callback` 등록 |
| 공급사 테스트 모드 | 필요한 경우 실제 테스트할 팀원의 계정 등록 |

앱 callback과 Supabase callback은 서로 다르다. 앱은 설정한 로컬 callback을 OAuth의 `redirect_to`로 보낸다. 허용 목록과 일치해야 한다. [Supabase Redirect URLs 문서](https://supabase.com/docs/guides/auth/redirect-urls)

이 프로젝트의 카카오 설정은 추가 이메일 scope를 요청하지 않으므로, 이메일 없는 사용자를 허용하는 Supabase 공급사 설정도 확인한다. 세부 내용은 [로그인 설계 §8](X3_로그인_설계.md#8-google카카오-가입로그인-2026-10-12)에 있다.

## 5. 성공 여부 확인

1. 같은 브라우저에서 `http://127.0.0.1:8000/api/auth/config`를 열어 `enabled: true`, `social_providers.google: true`, `social_providers.kakao: true`를 확인한다. 이 응답의 토큰 값을 공유할 필요는 없다.
2. 로그인 화면에서 카카오·Google 각각 **클릭 → 공급사 화면 → 뒤로가기 → 버튼 재클릭**을 확인한다. 수정 파일을 받은 기존 탭은 먼저 강력 새로고침한다(Windows: Ctrl+Shift+R).
3. 각자의 계정으로 로그인 → 앱 복귀 → 새로고침 후 로그인 유지 → 로그아웃 → 재로그인을 확인한다.
4. 테스트용 게스트 진입 → 새로고침 유지 → 로그아웃 → 새 게스트 진입을 확인한다. Supabase 모드의 이전 게스트 기록은 새 게스트에서 보이지 않아야 한다. 데모 모드는 서버 사용자 간 기록을 공유한다.

## 6. 막힐 때 구분하기

| 증상 | 확인할 것 |
|---|---|
| 로그인에 이메일 폼만 보임 | PR #71이 들어간 브랜치인지, 실제 실행한 저장소가 맞는지 확인 |
| Google·카카오 버튼이 처음부터 비활성 | 데모 모드인지, `/api/auth/config`의 공급사 활성 여부, Supabase 연결 확인 |
| 뒤로가기 후에만 비활성 | 최신 코드 pull 후 강력 새로고침. 실행 중인 서버가 다른 복사본을 제공하는지 확인 |
| `auth_origin` | 브라우저 주소와 `REGIME_AUTH_SITE_URL`의 호스트·포트가 같은지 확인 |
| 로그인 후 다른 주소로 복귀 | 앱 SITE_URL과 Supabase Redirect URLs의 정확한 callback 확인 |
| 팀원 계정만 거절됨 | 공급사 테스트 사용자/앱 이용 제한 확인 |
| 계정은 로그인됐지만 뉴스·분석이 비어 있음 | 시세 데이터 및 별도의 뉴스 조회 설정 확인 |

Supabase 계정은 공통 프로젝트에서 관리하지만 실행·전략·인증 소유자 파일은 각 로컬 서버에 저장된다. 같은 계정으로 다른 PC에 로그인해도 분석 결과가 자동 동기화되지는 않는다. 뉴스 DB 조회(PR #81) 역시 별도 설정이며, 로그인 테스트를 위해 n8n 수집기나 8765 브리지를 각 팀원 PC에 띄울 필요는 없다.
