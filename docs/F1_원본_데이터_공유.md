# F1 원본 데이터 팀 공유

> WBS F1 (담당 Seonghwanaa) · F1.1 공유 방식 비교 / F1.2 공유 구성·경로 설정 / F1.3 팀원 PC 재현 확인
> 기준: 2026-10-12, develop ff8522e. 숫자는 Seonghwanaa PC 에서 직접 확인한 값이다.
> 원본 데이터는 공개 저장소에 올리지 않는다. 서버 주소·접속 정보·키는 이 문서와 채널에 쓰지 않고 사람끼리 따로 전달한다.

## 1. 무엇이 필요한가

기능마다 필요한 자료가 다르다. 받는 사람은 쓰려는 기능의 줄만 받으면 된다.

| 자료 | 위치 (`engine/config/paths.local.yaml`) | 크기 | 쓰는 기능 | 없으면 |
|---|---|---|---|---|
| 일봉 본 데이터 `prices`·`marketcap`·`master`·`index`·`delisted`·`sample30` (.parquet) | `store` 폴더 | 약 100MB | 백테스트·역방향 탐색·서버 전체 | `data` 마커 테스트 skip, 서버·배치 실행 불가 |
| KRX 원주가·업종 `raw/krx_daily/` 1,483개, `raw/sector/` 148개 | `store` 폴더 아래 `raw/` | 약 530MB | 준비 프레임(소속부·업종), 1분봉 가격 기준 판정 | `prepare` 실패 |
| SQL 덤프 추출물 `cache/warmup/kor_price_*.parquet`, `cache/reference/*.parquet` | `cache` | 작음 | 지표 워밍업(A2), 상장 거래일(U1), 참조 지표 테스트 | 워밍업·참조 테스트 skip (원본 PC에도 아직 없음, §6) |
| 과거 지수 `cache/warmup/index_warmup.parquet` | `cache` | 약 20KB | 국면 2020-09-01부터(X5) | 국면이 2021-07-21부터 |
| 1분봉 사본 `stock_minutes_YYYYMM.parquet` 19개 + `minutes_manifest.json` | `store` 폴더 옆(같은 부모)의 `minutes/` (또는 `forecast-run --minutes`) | 약 3.0GB | 봉 예측(P2) | 봉 예측 실행 불가 (다른 기능은 영향 없음) |
| 외부 자료(공시) Parquet | `ext_store` (저장소 밖) | 인계 ZIP 약 105MB | 근거 검색·자료 보관함 | "데이터 없음" 표시 |
| SQL 덤프 `multi_tables_backup.sql` | `sql_dump` | 약 21GB | 위 추출물을 만들 때 한 번만 | 추출물을 받으면 필요 없음 |

- 일봉 본 데이터의 최신 거래일은 2026-09-18이다 (prices 3,865,943행·3,095종목, `collect.log`). 장 마감 증분 갱신은 X4에서 다룬다.
- 1분봉은 2025-03-27 ~ 2026-09의 362거래일, 237,308,896행이다 (MariaDB `stock_minutes` 읽기 전용 내보내기, `minutes_manifest.json`). 성질은 [`분봉_데이터_설계.md`](분봉_데이터_설계.md) §1에 있다.

## 2. 공유 방식 비교 (F1.1)

| 방식 | 내용 | 좋은 점 | 나쁜 점 | 판단 |
|---|---|---|---|---|
| A. 파일 묶음 직접 전달 | 위 표의 폴더를 압축해 사람끼리 비공개로 전달하고, 받는 사람이 경로만 지정 | 엔진이 읽는 형식 그대로, 인터넷·서버 없이 재현, 해시로 같은 자료인지 확인 가능 | 갱신할 때마다 다시 전달, 1분봉은 3GB | **기본 방식** |
| B. 데이터 서버 조회 API | 데이터 PC의 MariaDB 앞에 둔 조회 전용 API (허용한 IP만, 행 수 제한, 쓰기 없음) | 파일 없이 종목·기간을 골라 조회, 10-07 sample30 실데이터 회귀에 사용(#28) | 엔진은 Parquet만 읽으므로 그대로 백테스트에 못 씀, 서버 PC가 켜져 있어야 함 | 확인·대조용 |
| C. SQL 덤프 전체 전달 | 21GB 덤프를 넘기고 각자 추출 | 원래 자료 전체 | 크기, 추출에만 쓰고 본 데이터(`store`)는 따로 필요 | 쓰지 않음 (추출물로 대신) |

- 엔진 입력 계약은 Parquet(`store`)이다. DB(MariaDB)는 조회용 사본이며 엔진은 DB를 읽지 않는다. DB를 원본으로 바꾸려면 엔진 입력 변경과 쓰기 권한을 따로 정해야 한다.
- 지금까지 만든 묶음: `store/raw/krx_daily`·`raw/sector` 묶음(약 217MB, 풀 위치 설명 포함). 일봉 본 데이터·1분봉·SQL 덤프 추출물은 따로 묶는다.

## 3. 경로 설정 (F1.2)

1. `engine/config/paths.example.yaml` 을 `engine/config/paths.local.yaml` 로 복사한다 (Git 제외).
2. 받은 폴더 위치를 적는다. 상대 경로는 저장소 루트 기준이다. 저장소 루트의 `data/` 아래에 두는 예:

```yaml
store: data/store            # prices.parquet 이 있는 폴더. raw/krx_daily·raw/sector 는 이 안에
sql_dump: data/raw/multi_tables_backup.sql   # 추출물을 받았으면 없어도 됨
cache: cache                 # cache/warmup·cache/reference 를 여기에 풀기
runs: runs
ext_store: ../regime-lab_ext_store          # 공시 자료 (저장소 밖)
```

- 1분봉은 설정 키가 따로 없다. `store` 폴더와 같은 부모 폴더의 `minutes/` 를 기본으로 읽는다 (`data/store` 이면 `data/minutes`). 다른 곳에 두면 `regime-lab forecast-run --minutes <폴더>` 로 지정한다.
- `paths.example.yaml` 의 기본값은 `store: store` 이고 README 는 저장소 루트의 `data` 를 말한다. 어느 쪽이든 `store` 가 `prices.parquet` 이 있는 폴더를 가리키면 된다.
- 복사한 파일은 수정 시각이 바뀌므로 준비 프레임 캐시는 받는 PC에서 한 번 새로 만든다 (`input_file_hashes` 가 Parquet 은 크기·수정 시각을 본다). 정상이다.

## 4. 재현 확인 (F1.3)

받는 사람이 아래를 차례로 확인한다. 하나라도 다르면 보낸 사람에게 숫자를 알려 준다.

| 확인 | 방법 | 기대값 (보낸 PC) |
|---|---|---|
| 파일 수·크기 | 탐색기 또는 아래 명령 | `prices.parquet` 79,424,775바이트, `marketcap.parquet` 24,371,566바이트, `master.parquet` 85,880바이트, `index.parquet` 116,277바이트, `delisted.parquet` 12,053바이트 |
| 원주가·업종 해시 | `uv run --project engine python -c "from regime_lab.data.loader import input_file_hashes as f; from regime_lab.config import load_paths as p; print(f(p().store))"` | `raw/krx_daily` n=1483·sha256 `ee4e035a08ec4ca4`, `raw/sector` n=148·sha256 `6388ba9796154ca0` |
| 1분봉 | `minutes/` 에 `stock_minutes_202503.parquet` ~ `stock_minutes_202609.parquet` 19개 + `minutes_manifest.json` | 매니페스트 `total_rows` 237,308,896 |
| 검증값 | `collect.log` 의 검증 항목 | 삼성전자(005930) 2021-01-04 종가 83000, 시작일 2020-09-01, 거래대금·종가 결측 0 |
| 테스트 | `uv run --project engine python -m pytest engine -m data -rs` | 추출물까지 있으면 skip 0. 보낸 PC는 19 passed·29 skipped이고, 29개는 모두 `cache/warmup`·`cache/reference` 없음(SQL 덤프 추출물) 때문이다. `-rs` 로 skip 사유를 보면 어느 자료가 빠졌는지 알 수 있다 |
| 준비 | `uv run --project engine regime-lab prepare` | 오류 없이 끝남 |
| 봉 예측(선택) | `uv run --project engine regime-lab forecast-run --timeframe 1h --sample` | `runs/forecasts/1h-…` 생성 (sample30 중 1분봉이 있는 28종목) |

전 종목 봉 예측 실행 비용(실측, 같은 PC): 1h 300종목 232초·최대 메모리 4.3GB(`forecast.runs.batch_codes` 200). 묶음을 50으로 줄이면 최대 2.0GB이고 결과는 같다. 전 종목 2,725개는 1h 약 35분으로 추정한다(미실측).

## 5. 하지 말 것

- 원본 데이터·1분봉·추출물·공시 원문을 저장소에 커밋하지 않는다 (공개 저장소, `AGENTS.md` §7).
- `regime.duckdb` 는 열지 않는다. Parquet 만 읽는다.
- 서버 주소·IP·DB 계정·키를 문서·채널·PR 에 쓰지 않는다.
- 받은 원본 파일을 고치거나 옮기지 않는다. 다시 받아야 하면 보낸 사람에게 새 묶음을 요청한다.
