# 프로젝트 1 — 역방향 백테스트(목표 승률 → 조건 찾기)와 찾은 조합 저장

> 상태: 계획안 · 예상 6~11인주 · 선행: [전체 계획](README.md)의 계약·규칙 결정. 기존 일봉 백테스트를 기준으로 설명한다. 쉬운 설명은 [설명회 자료](00-explainer.md)를 본다.

## 현재 상태·목표

### 정방향과 역방향

| | 현재 백테스트 (정방향) | 이 프로젝트 (역방향) |
|---|---|---|
| 입력 | 조건: 패턴·AND/OR·청산·시장·기간 | **목표 승률** `N% 이상`과 탐색할 조건 범위 |
| 처리 | 입력한 조건으로 백테스트 1회 | 조건 조합의 경우의 수를 생성해 백테스트를 반복 |
| 출력 | 그 조건의 승률·성과 | 과거에 목표 승률을 충족한 **조건 조합 목록**과 탐색 기록 |

```text
정방향: 조건 ──▶ 백테스트 ──▶ 승률
역방향: 목표 승률 + 탐색 범위 ──▶ 후보 조합 생성 ──▶ 후보별 백테스트(기존 엔진) ──▶ 목표 충족 조합
```

이 프로젝트의 중심은 **역방향 백테스트**다. 사용자가 조건을 하나씩 바꿔 넣고 승률을 확인하는 반복을 도구가 대신한다. 찾은 조합을 이름 붙여 저장하는 프리셋 기능은 탐색 결과를 보관·재사용하기 위한 후속 기능이다.

### 확인된 출발점

- 핵심 패턴은 `engine/src/regime_lab/patterns/core.py`의 5종이다: `ma_cross_5_20`, `breakout_20d`, `breakout_vol`, `rsi_rebound`, `bb_lower_recover`.
- 패턴 수치(`breakout_vol.volume_mult`, `rsi_rebound.threshold` 등)는 `engine/config/default.yaml`의 전역 값이다. 전략별로 바꿀 수 없다.
- 전략은 패턴 이름 목록, AND/OR(`combine`), 청산(`stop_loss_pct`, `take_profit_pct`, `max_hold_days`), 유니버스 설정을 받는다. 청산 허용 범위는 `exit_limits`에 있다. `api/src/regime_api/schemas.py`는 5개 패턴 이름만 허용하고 한 요청의 전략 수를 제한한다.
- 승률은 `집계 포함 거래 중 net_ret > 0 거래 수 / 집계 포함 거래 수`다. 비용은 차감하고, 기준일에 보유 중이라 제외된 거래는 분모에 넣지 않는다.
- 3중 검증(기간 분할·FDR·무작위 벤치마크)은 실행마다 수행하며, FDR 가족 크기 m은 한 요청의 전략 수다.
- 실측 성능: 캐시 적재 후 단일 전략 약 13초, 핵심 5종 비교 약 75초(`docs/구현_계획.md`).
- 웹 전략 빌더 입력은 세션 초안이다. 이름 붙인 조합의 영구 저장·목록·삭제는 없다.

### 목표

1. 사용자가 **목표 승률 `N% 이상`** 과 **탐색 범위**를 지정하면, 도구가 범위 안의 조건 조합을 생성해 **기존 백테스트와 같은 규칙**으로 평가하고 목표를 충족한 조합을 찾는다.
2. 찾은 조합은 탐색 구간 성적과 **탐색에 쓰지 않은 후속 평가 구간** 성적을 함께 보여 준다. 시도한 조합 수를 공개해 우연히 높은 승률과 구분할 수 있게 한다.
3. 찾은 조합을 이름 붙여 저장·불러오기·수정·삭제하고, 탐색 1회의 입력과 결과를 기록으로 남긴다.

역방향 백테스트는 **조건 최적화**다. 기존 SRS는 고정 파라미터와 최적화 제외를 명시하므로, 승인된 개정 전에는 이 문서의 계획만 유효하다.

## 탐색 범위: 섞어 볼 재료

역방향 백테스트가 경우의 수를 만드는 축이다. 어떤 축을 열고 각 축의 허용 값·범위를 얼마로 둘지는 D-1에서 확정한다.

| 축 | 현재 상태 | 탐색 후보(D-1 확정 전 예시) |
|---|---|---|
| 패턴 선택 | 5종 중 선택 | 5종 중 1개 이상을 고르는 부분집합 |
| 결합 방식 | `and` / `or` | 두 개 이상 선택 시 AND·OR |
| 패턴 수치 | 전역 설정 고정 | 이평 단기·장기 기간, 돌파 참조 기간, 거래량 배수, RSI 문턱, 볼린저 기간·배수 |
| 청산 | 전략별 입력, `exit_limits` 범위 | 손절 %, 익절 %, 최대 보유일의 이산 값 목록 |
| 시장·기간 | 전략별 입력 | 사용자가 고정해 두는 조건. 탐색 축으로 열지는 D-1에서 결정 |

**경우의 수는 곱으로 커진다.** 패턴 부분집합 31개 × AND/OR × 청산 값 몇 개씩만 곱해도 수백~수천 개가 된다. 패턴 수치까지 열면 더 커진다. 실측 13초/전략으로 단순 반복하면 300개 조합에 약 1시간이 걸린다. 따라서 다음을 구현 전에 정한다.

- **후보 생성 방식:** 범위 안의 이산 값을 모두 도는 전수 탐색을 기본으로 한다. 전수 탐색 수가 상한을 넘으면 실행 전에 알리고 범위를 줄이게 한다. 무작위 표본·단계적 탐색은 D-1에서 필요성이 확인될 때만 쓰고, 쓰면 시드와 방식을 기록한다.
- **상한:** 1회 탐색의 최대 후보 수와 예상 소요 시간 상한.
- **비용 절감:** 준비 프레임과 지표를 후보 간에 재사용한다. 후보별 결과 폴더 저장과 전체 3중 검증을 모든 후보에 돌릴지, 목표 충족 후보에만 돌릴지 정한다. 어느 쪽이든 FDR 가족 크기는 **시도한 전체 후보 수**로 둔다.

## 작업 ① — 데이터·계약 확인 (1~2인주)

1. 현재 전략 입력, 기본 수치, 결과 저장, API 응답, 웹 빌더 상태와 핵심 5종의 수치 의존성을 목록화한다.
2. 위 "탐색 범위" 표의 축별 허용 값·범위·조합 제약(예: 단기 기간 < 장기 기간)을 D-1로 확정한다.
3. 공통 지표가 고정 기간으로 미리 계산되는 경로를 확인한다. `sma5`, `sma20`, `high_max_prev20`, `rsi14` 같은 준비 프레임 열은 기간이 이름에 박혀 있다. 기간을 탐색하려면 후보별 지표 계산 또는 여러 기간의 사전 계산이 필요하다. `pipeline.py`의 준비 프레임·캐시·종목별 rolling 값에 영향이 있으면 `PREP_VERSION` 변경과 종목별 절단 불변 테스트를 계획한다.
4. 승률 정의를 현재 코드와 결과 화면 기준으로 고정하는 회귀 테스트를 둔다. 비용 차감, 제외 거래, 수익 0 거래의 처리도 동일하게 둔다. 목표 판정은 이 승률과 **같은 값**을 쓴다.
5. 탐색 구간과 후속 평가 구간을 나누는 방식(날짜 경계, 비율, 기존 기간 분할과의 관계)을 정한다.
6. 탐색 기록과 저장 조합의 위치·범위(이 PC 전체, 브라우저별), 이름 충돌·삭제 정책, 기존 전략 YAML과의 관계를 정한다. 현재 로그인은 데모이므로 사용자별 권한을 전제로 설계하지 않는다.

**완료 기준:** 탐색 축·허용 범위·상한, 평가 구간 분할, 탐색 기록·저장 계약, 기존 실행 형식과의 호환 방식이 문서와 테스트 사례로 확정된다.

## 작업 ② — 역방향 백테스트 (3~6인주)

### 계산·검증 흐름

1. 사용자가 목표 승률 `N% 이상`, 탐색 범위(축별 값 목록), 시장·기간, 최소 거래 수를 입력한다.
2. 엔진이 범위 안의 유한한 후보 조합을 생성한다. 실행 전에 후보 수와 예상 시간을 반환하고, 상한을 넘으면 실행하지 않는다.
3. 후보마다 **기존 백테스트 엔진**으로 동일한 신호·체결·비용·제외 거래 규칙을 적용해 탐색 구간의 승률과 거래 수를 계산한다. 탐색용 별도 체결·승률 계산을 만들지 않는다.
4. 탐색 구간에서 목표를 충족하고 최소 거래 수를 넘은 후보만, **탐색에 쓰지 않은 후속 평가 구간**에서 다시 평가한다. 평가 구간의 결과는 후보 선택·재탐색에 쓰지 않는다. 같은 평가 구간을 반복 탐색의 기준으로 재사용하지 않는다.
5. 3중 검증을 적용할 때 FDR 가족 크기는 시도한 전체 후보 수다. 최종 선택 후보 수로 줄이지 않는다.
6. 결과를 다음 상태로 구분한다: `탐색·평가 모두 충족`, `탐색만 충족`, `거래 수 부족`, `미충족`. 목표를 충족한 후보가 없으면 가장 가까운 후보와 부족한 항목(승률, 거래 수)을 표시한다.
7. 탐색 1회마다 목표, 탐색 범위, 생성 방식, 시도 후보 수, 구간 경계, 데이터 기준일, 시드(쓴 경우), 결과 요약을 탐색 기록으로 남긴다. 같은 입력과 데이터로 다시 돌리면 같은 결과가 나와야 한다.
8. 긴 탐색은 현재의 "작업 1개·취소 가능" 정책 안에서 돈다. 진행률은 처리한 후보 수 / 전체 후보 수만 표시한다. 취소하면 그때까지의 결과를 `중단됨`으로 기록하고 완료된 탐색처럼 보이지 않게 한다.

### 화면에서 보이는 모습

- **역방향 백테스트 화면:** 목표 승률 입력, 축별 탐색 범위 선택(패턴 체크, AND/OR, 패턴 수치 범위, 청산 값 목록, 시장·기간), 최소 거래 수, 예상 후보 수·소요 시간, 실행·취소 버튼.
- **진행 표시:** 처리 후보 수 / 전체 후보 수, 지금까지 목표를 충족한 수.
- **결과 표:** 조합 내용(패턴·결합·수치·청산), 탐색/평가 기간, 거래 수, 두 구간의 승률, 3중 검증, 상태. 정렬 기준을 화면에 명시하고, 승률만으로 `추천` 순위를 만들지 않는다. 표 위에 시도 후보 수와 "과거 결과이며 미래 성과를 보장하지 않는다"는 고지를 둔다.
- **후보 상세:** 후보 하나를 기존 결과 화면 형식(국면별 성과, 손익 분포 등)으로 열어 볼 수 있다.
- **저장:** 후보를 선택해 이름을 붙여 저장한다(작업 ③).

**완료 기준:** 목표 판정이 현재 `win_rate` 정의와 일치한다. 합성 데이터에서 후보 생성·축별 경계·상한 초과·무후보·취소·재현성이 검증된다. 평가 구간 데이터를 바꿔도 탐색 구간의 후보 선택이 변하지 않는다. 후보 하나를 기존 정방향 실행으로 돌리면 같은 탐색 구간 승률이 나온다.

## 작업 ③ — 찾은 조합의 저장과 재사용 (2~3인주)

### 계산·저장 흐름

- 패턴 이름만 담는 현 전략 표현에 패턴별 **수치**를 실을 수 있도록 공개 계약의 개정안을 만든다. 기존 전략 파일과 과거 `run_id` 결과는 읽기·표시 가능해야 한다. 저장 형식·API를 바꾸므로 `AGENTS.md` §9의 사전 결정 대상이다.
- `engine/config/default.yaml`은 확정된 기본 수치의 기준으로 유지한다. 조합의 수치는 그 실행에만 적용되는 값으로 저장하고 결과 메타데이터에 기록한다. 기본값의 확정·확인 대기 값은 임의로 수정하지 않는다.
- 저장한 조합에는 어느 탐색 기록에서 왔는지(또는 직접 만들었는지)를 남긴다. 저장 후 조합을 수정해도 과거 실행 결과·탐색 기록은 바뀌지 않도록, 실행 시 사용한 값의 스냅샷을 남긴다.
- 인프라가 저장을 맡고, 엔진 도메인이 조합의 수치를 검증한다. API 진입은 입력 검증·유스케이스 호출·응답 변환에 한정한다. 정확한 저장 파일·모듈 위치와 새 역할은 구현 전 구조 검토로 확정한다.

### 화면에서 보이는 모습

1. **저장 목록:** 이름, 조합 요약, 출처(탐색 기록 / 직접 작성), 수정 시각. 불러오기·이름 변경·덮어쓰기/별도 저장·삭제를 구분한다. 저장하지 않은 변경이 있으면 전환 전에 알린다.
2. **전략 빌더 연결:** 저장한 조합을 빌더로 불러와 정방향으로 다시 실행하거나, 패턴 카드의 `세부 조건`에서 수치를 고쳐 새 이름으로 저장한다. 항목마다 단위·기본값·허용 범위·값 오류를 바로 표시한다.
3. **탐색 기록 목록:** 과거 탐색의 목표, 범위, 시도 수, 결과 요약을 다시 열어 본다.
4. **실행 결과:** 사용한 조합의 실제 수치와 데이터 기준일을 열람할 수 있다. 과거 결과에는 기존 형식임을 표시한다.
5. 한국어가 기본이고 영어 전환 시 문구가 함께 바뀐다. 키보드로 수치 편집·저장·목록 조작이 가능해야 한다.

**완료 기준:** 탐색 결과 저장 → 새로고침/재접속 → 불러오기 → 수정 → 재실행에서 같은 값이 유지된다. 잘못된 수치는 웹과 API에서 같은 이유로 거부된다. 기존 기본 전략의 성과는 변하지 않는다.

## 책임·의존성 및 동작 보존

| 역할 | 변경할 책임 | 보존/확인할 동작 |
|---|---|---|
| 엔진 도메인 | 탐색 범위 검증, 후보 조합 생성, 패턴 수치 검증·신호, 구간 분할 평가 | t일 신호에 미래값 미사용, 종목별 rolling, RSI 기본 `sma`, 현재 체결·비용·승률 정의 |
| 엔진 유스케이스 | 탐색 실행·진행·취소·탐색 기록, 결과 스냅샷 | 기존 전략 실행·결과 재현성 |
| 인프라 | 탐색 기록·저장 조합 보관 | 원본 데이터 무변경, 기존 결과 폴더 형식 호환 |
| API 진입·조립 | 역방향 탐색·저장 계약, 요청 연결 | 기존 `/api/runs` 계약의 호환·이전 방식 |
| 웹 진입·공유 | 탐색 입력·진행·결과, 저장 목록 표시, i18n | 기존 빌더·결과·취소 흐름과 접근성 |

새 모듈·저장 위치·API·결과 형식은 아직 정하지 않았다. 필요한 책임과 의존성, 기존 테스트 보존 방식을 먼저 제시해 `AGENTS.md` §9에 따라 결정받는다. 기본 파라미터를 코드 상수로 옮기지 않는다.

## 위험·결정 대기

- **과적합:** 역방향 백테스트는 시도 후보가 많을수록 탐색 구간 승률이 부풀기 쉽다. 최소 거래 수, 후보 수 상한, 별도 평가 구간, FDR 가족 크기 기준을 확정해야 한다.
- **계산 비용:** 실측 13초/전략으로는 수백 개 후보가 1시간 단위로 늘어난다. 준비 프레임 재사용, 후보별 저장 생략, 검증 범위를 설계하지 않으면 탐색이 실용적이지 않다. 탐색을 일반 실행 여러 번으로 무제한 호출하지 않는다.
- **지표 기간 탐색:** 이평·돌파·RSI 기간을 열면 준비 프레임 구조와 캐시가 바뀐다. 첫 단계에서는 준비 프레임을 바꾸지 않는 축(패턴 선택, AND/OR, 거래량 배수·RSI 문턱, 청산)만 여는 방안도 D-1에서 검토한다.
- **저장 범위:** 데모 로그인에 사용자 식별이 없다. 다중 사용자 저장·권한을 암묵적으로 도입하지 않는다.
- **범위 충돌:** 기존 SRS는 고정 파라미터와 최적화 제외를 명시한다. 승인된 개정 전에는 계획만 유효하다.
