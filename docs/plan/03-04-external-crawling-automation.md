## 1. 결론 요약

| 질문 | 제안 |
|---|---|
| 무엇부터 모으나 | **① 공시(OpenDART) → ② 뉴스 헤드라인(RSS·네이버 검색 API) → ③ SNS(선택)**. 공시는 공식 API로 5년 전체를 소급할 수 있어 프로젝트 3의 일봉 5년 학습에 바로 쓸 수 있다 |
| 먼저 정할 것 | **이용 목적(비영리 연구·시연 / 상업 서비스)**. RSS 공개가 영리적 재사용 허가는 아니므로, 목적이 정해져야 출처별 사용 가능 여부를 판정할 수 있다 |
| 가장 급한 것 | 허가가 확인된 뉴스 피드가 생기면 **순방향 수집을 일찍 켠다**. RSS·검색 API는 과거를 거의 돌려주지 않는다. 1분봉(최근 약 1.5년) 구간의 과거 뉴스는 소급 가능한 출처로만 채울 수 있고, 순방향 수집은 시작이 늦을수록 이후 갱신될 분봉과 겹치는 기간이 줄어든다 |
| 어떻게 긁나 | 허가된 **API·RSS만** 호출한다. HTML 페이지 스크래핑(포털 뉴스 본문, 종목토론방 등)은 제외한다 |
| 어떻게 자동화하나 | 수집기를 **CLI 명령 1개**로 만들고 OS 스케줄러(Windows 작업 스케줄러·cron)가 주기 실행한다 |
| 시각은 어떻게 다루나 | `published_at`(출처가 준 시각)·`first_seen_at`(내 수집기가 처음 발견한 시각)·`available_at`(분석에 쓸 수 있는 시각)을 분리한다. **`first_seen_at`은 공시 접수 시각이 아니고, 네이버 `pubDate`는 원문 최초 게시 시각이 아니다** |
| 브리핑(프로젝트 4)은 | 지정 시각 T에 수집 마감 → **스냅샷 고정** → 집계 → 검증 → 발행 |

## 3. 전체 흐름

```text
 OS 스케줄러 (작업 스케줄러 / cron)
   │  regime-ingest run --source opendart   (소스별 주기 실행)
   ▼
[1 수집] 소스 어댑터: 커서(마지막 수집 지점)부터 창 겹침 조회 · 속도 제한 · 재시도
   ▼
[2 원본 보관] raw/<source>/<date>/<ingest_run_id>.jsonl.gz   ← 허용 범위만, 덮어쓰지 않음
   ▼
[3 정규화] 공통 문서 스키마로 변환 (출처 ID·제목·요약·URL·시각·시각 기준)
   ▼
[4 중복·버전] 출처 ID·정규화 URL·내용 지문으로 중복 제거, 정정·수정은 버전으로 연결
   ▼
[5 종목 연결] 종목코드(공시) / 종목명 사전(뉴스) + 근거 기록, 모호하면 '미확정'
   ▼
[6 품질·공백 검사] 소스×시간 구간별 수집 여부 기록 — 실패 구간은 '공백'으로 표시
   ▼
[7 사용 가능 자료] docs/ (Parquet, available_at 포함)  ──→ 프로젝트 3 특징·RAG 색인
                                                     └─→ 프로젝트 4 브리핑 스냅샷
```

단계 1~6은 **수집 파이프라인**, 7 이후의 특징 추출·가중치 학습·RAG 색인은 프로젝트 3의 별도 산출물이다. 수집 실패가 학습·색인을 조용히 비우지 않도록 7은 6의 공백 표시를 함께 넘긴다.

## 4. 시각 계약 (시점 누출 방지의 핵심)

| 필드 | 뜻 | 출처 |
|---|---|---|
| `published_at` | 출처가 준 시각 (없으면 날짜만) | 응답 값 |
| `published_at_basis` | 그 시각이 무엇을 뜻하는지: `dart_receipt_date`(접수일, 날짜만) · `naver_provided`(네이버 제공 시간) · `feed_pubdate`(피드가 밝힌 게시 시각) · `message_date`(SNS 메시지 시각) | 출처별 고정 |
| `time_precision` | `second` / `minute` / `date_only` | 파싱 결과 |
| `modified_at` | 출처가 밝힌 수정 시각 | 응답 값(있을 때) |
| `first_seen_at` | 내 수집기가 이 자료(해당 버전)를 **처음 발견한** 시각. 실제 공시 접수·기사 게시 시각이 아니다 | 수집기 시계 |
| `available_at` | 분석·학습·브리핑에서 이 자료를 쓸 수 있는 시각 | 아래 규칙 |
| `backfilled` | 과거 소급 수집 여부 | 수집 모드 |

**`available_at` 규칙 (제안)**

1. **순방향 수집:** `available_at = first_seen_at`. 내가 실제로 가지고 있던 시점부터만 쓰므로 누출이 없다. 실제 공개 시각보다 **폴링 간격 + 출처 반영 지연만큼 늦을 수 있다**(보수적). 이 지연은 §11 1단계에서 KIND 화면 시각과 대조해 측정·기록한다.
2. **소급 수집(`backfilled = true`):** `first_seen_at`이 의미 없으므로 `published_at`에 보수적 규칙을 적용한다.
   - `date_only`(OpenDART 소급분): 그날 **장 마감 이후**로 보고 다음 거래일 첫 봉부터 연결한다. 장중 공시의 당일 반응은 잃지만, 장 마감 뒤 공시를 당일 봉에 붙이는 누출보다 안전하다.
   - 시·분이 있는 자료(빅카인즈 등, 채택 시): `published_at + 지연 여유`(값은 설정 파일, 확인 후 결정).
   - `naver_provided`: 원문 최초 게시보다 늦을 수 있는 시각이므로 **시점 누출 방향으로는 안전**하지만, 영향력 학습에서 "원문 공개 시각"으로 해석하지 않는다.
3. **가격 봉 연결:** `available_at`보다 **시작 시각이 늦은 첫 봉**에 붙인다. 장 마감 후·휴장일 자료는 다음 거래일 첫 봉으로 넘긴다.
4. **정정·수정본**은 새 버전의 `available_at`을 따로 가진다. 과거 시점 계산은 그 시점에 존재한 버전만 본다.
5. **세션 기준**은 가격 데이터와 같게 한다(KRX 정규장 09:00~15:30 KST 가정). 대체거래소 프리·애프터마켓 시간 포함 여부는 프로젝트 2의 1분봉 실사 결과로 정한다.
6. **일봉 학습의 시간 차이:** 순방향 수집 자료만 분 단위 정밀도를 가진다. 5년 소급 공시는 날짜 단위라 **일봉 학습에만** 쓰고, 분봉 학습에는 순방향 수집분만 쓴다.

**거래일 달력:** 과거 구간은 보유 시세 데이터의 실제 거래일을 쓴다. 브리핑처럼 미래 날짜가 필요한 경우의 휴장일 목록 출처는 D-5에서 정한다.

## 6. 소스별 수집 방법

### 6.1 OpenDART 공시 (1순위)

- **순방향:** 거래일 07:00~20:00(KST)에 짧은 주기(예: 2~5분)로 당일 공시 목록(`bgn_de=end_de=오늘`, `corp_cls`별)을 끝 페이지까지 조회하고, 그 밖의 시간은 간격을 늘린다. 새 `rcept_no`를 `first_seen_at`과 함께 저장한다. 주기는 요청 제한(오류 `020`) 안에서 정하고 설정 파일에 둔다.
- **소급:** `corp_code` 없이 조회하면 검색기간이 최대 3개월이므로 **1개월 이하 창**으로 나눠 `page_count=100`으로 끝 페이지까지 받는다. `corp_cls`를 유가(Y)·코스닥(K)으로 제한한다. 하루 요청 수 상한을 두고, 끊겨도 커서에서 이어 받는다. 소급분은 `backfilled = true`, `time_precision = date_only`.
- **종목 연결:** 공시에 `stock_code`가 있어 `native` 연결이 가능하다. 고유번호 ZIP을 주기적으로 받아 상장폐지·코드 변경을 반영하고, 보유 종목 마스터와의 매칭률을 기록한다.
- **정정 공시:** 보고서명의 정정 표시(예: `[기재정정]`)와 원공시 관계를 버전으로 연결한다.
- **원문:** 원본파일 ZIP은 용량이 커서 기본은 **목록 메타데이터만** 받는다. 원문이 필요한 공시 유형(`pblntf_ty`·`pblntf_detail_ty`)을 정한 뒤 선택 수집한다.
- **의존성:** 표준 라이브러리(`urllib`, `json`, `zipfile`, `xml.etree`)로 구현 가능하다.

### 6.2 뉴스 (2순위)

- **RSS:** 이용 조건이 확인된 피드만 5~10분 주기로 읽는다. `ETag`·`Last-Modified`로 조건부 요청을 하고 제목·요약·링크·게시 시각만 저장한다.
- **네이버 검색 API 보조:** 관심 종목의 종목명 질의를 `sort=date`로 낮은 빈도로 돌려 RSS에 없는 기사를 보완한다. 일 한도(검토 인용 25,000회)를 종목 수와 주기로 나눠 대상 범위를 정한다(예: 300종목 × 30분 간격 × 장중·장후 16시간 ≈ 9,600회/일). `originallink`를 원출처로 저장하고 `pubDate`는 `naver_provided`로 표시한다.
- **과거 소급:** RSS·네이버 API로는 할 수 없다. 빅카인즈 확인(§11 0-4)이 끝나기 전에는 뉴스 기반 영향력 학습을 **순방향 수집 시작일 이후**로 한정한다고 문서·화면에 밝힌다.
- **종목 연결:** 보유 종목 마스터의 종목명·약칭 사전으로 제목·요약을 매칭한다. 일반 명사와 겹치는 이름·그룹명은 `ambiguous`로 두고 학습 입력에서 뺀다. 매칭 근거 문자열을 `evidence`에 남긴다.
- **근사 중복:** 같은 보도자료를 여러 언론사가 옮긴 경우 `cluster_id`로 묶어 한 사건이 여러 번 가중되지 않게 한다. 묶음의 `available_at`은 가장 이른 구성원의 값이다.

### 6.3 SNS (3순위, 선택)

- 포함 여부 자체가 D-4c 결정이다. 포함한다면 **채널 단위 허용 목록**(공개 채널, 운영 주체 확인)을 두고 공식 클라이언트 API로만 받는다.
- 작성자 식별자는 가명 처리하고, 개인 계정·비공개 그룹은 수집하지 않는다. 삭제된 메시지는 다음 수집에서 `deleted` 버전으로 기록하고 검색·브리핑에서 뺀다.

## 7. 자동화·운영

### 7.1 실행 방식

| 방식 | 장점 | 단점 | 제안 |
|---|---|---|---|
| **OS 스케줄러 + CLI** (`regime-ingest run --source <x>`) | 새 의존성 없음, API 서버와 독립, 서버 재시작 영향 없음, 실패가 실행 단위로 분리 | 스케줄 정의가 저장소 밖(OS)에 있음 → 등록 스크립트·문서 필요, 수집 PC가 켜져 있어야 함 | **채택 제안** |
| API 서버 안의 스케줄러 | 한 프로세스로 관리 | 현재 작업 관리자(1개 실행·취소)와 충돌, 서버를 끄면 수집 중단 | 제외 |
| 워크플로 도구(Airflow·Prefect 등) | 대규모 운영 기능 | 과한 인프라, `AGENTS.md` §7 취지와 맞지 않음 | 제외 |

- 같은 소스의 중복 실행은 잠금으로 막는다. 이미 실행 중이면 새 실행은 `skipped`로 기록하고 끝낸다.
- 창 겹침 조회(직전 커서보다 조금 앞부터)를 하고 중복 제거에 맡긴다. 같은 창을 두 번 돌려도 자료 수가 늘지 않아야 한다(멱등).

### 7.2 요청 예절과 실패 처리

- 소스별 **요청 간격·일 한도**를 설정 파일에 두고 지킨다. `429`·`Retry-After`·OpenDART `020`을 따르고, 일시 오류는 지수 백오프로 재시도한다(횟수 상한).
- 식별 가능한 `User-Agent`를 쓰고, RSS는 `robots.txt`를 확인한다.
- 인증키는 **환경변수로만** 받는다(`DART_API_KEY`, `NAVER_CLIENT_ID`·`NAVER_CLIENT_SECRET` 등 이름은 구현 시 확정). 오류 문구의 키 조각은 기존 LLM 오류 처리처럼 가린다.

### 7.3 수집 기록과 공백 표시

| 기록 | 내용 |
|---|---|
| `ingest_runs` | 실행 ID, 소스, 조회 창, 시작·끝 시각, 받은 수·신규·중복·버전 증가·오류 수, 상태(`ok`/`partial`/`failed`/`skipped`) |
| `coverage` | 소스 × 1시간 구간별 `collected` / `gap` / `not_scheduled` |
| `cursors` | 소스별 마지막 수집 지점, 조건부 요청 헤더 값 |
| `seen_keys` | 중복 판별 키(출처 ID·URL 해시·내용 지문)와 최신 버전 |

학습·브리핑은 `coverage`의 `gap` 구간을 **자료 없음과 구분**해 받는다.

### 7.4 저장 위치 (제안, §9 승인 대상)

```text
<ext_store>/                     ← paths.local.yaml에 경로 지정, Git 제외
  raw/<source>/<YYYY-MM-DD>/<ingest_run_id>.jsonl.gz   원본 응답(허용 범위), 추가만
  docs/source=<source>/date=<YYYY-MM>/part-*.parquet   정규화·버전 포함 사용 가능 자료
  state.sqlite                                         ingest_runs·coverage·cursors·seen_keys
```

- 원본 시세 데이터(`store/`, `multi_tables_db/`)와 **다른 폴더**에 둔다. `regime.duckdb`는 쓰지 않는다.
- 보관 만료·삭제 요청이 오면 `docs`에서 해당 버전을 `deleted` 처리하고, RAG 색인·브리핑 캐시에 삭제를 전파하는 목록을 남긴다.

## 8. 코드 배치 (제안, §9 승인 대상)

수집은 네트워크·파일·시계를 쓰는 **인프라** 작업이라 R2에 따라 인프라에만 둔다. 현재 엔진은 네트워크를 쓰지 않으므로 **A안을 제안**한다.

| 안 | 위치 | 장점 | 단점 |
|---|---|---|---|
| **A** | 새 최상위 패키지 `ingest/` (`engine`·`api`와 같은 급, 자체 `pyproject.toml`, CLI `regime-ingest`) | 엔진을 네트워크 없는 결정적 계산으로 유지, 수집 의존성이 엔진·API에 섞이지 않음 | §2 구조 지도에 새 행 필요(`/agents-md` 개정) |
| B | `engine/src/regime_lab/data/external/` | 기존 인프라 폴더 재사용 | 엔진에 네트워크·스케줄 책임이 들어감 |

| 역할 | 위치(A안) | 책임 |
|---|---|---|
| 진입 | `ingest/.../cli.py` | `run --source`, `backfill --source --from --to`, `status` |
| 유스케이스 | `ingest/.../collect.py` | 커서 → 수집 → 원본 보관 → 정규화 → 중복·버전 → 종목 연결 → 기록 |
| 도메인 | `ingest/.../normalize.py`, `dedup.py`, `timing.py`, `tagging.py` | I/O 없는 순수 계산: 시각 규칙·중복 판별·종목 매칭 (단위 테스트 대상) |
| 인프라 | `ingest/.../sources/<출처>.py`, `store.py` | 출처별 HTTP 호출, Parquet·SQLite 읽기·쓰기 |

- 엔진·API는 수집 패키지를 import하지 않고 **저장된 Parquet만 읽는다**. 수집 패키지도 엔진을 import하지 않는다. 종목 마스터는 파일로 내보낸 사전을 읽는다.
- 소스 어댑터 공통 인터페이스는 1단계(공시만)에서는 만들지 않고 2번째 출처를 붙일 때 추출한다(R7).
- 새 외부 의존성 후보: RSS 파서(`feedparser`), HTTP 클라이언트(`httpx`), 텔레그램 클라이언트. 1단계는 표준 라이브러리로 시작하고 필요해질 때 하나씩 승인받는다.

## 9. 프로젝트 4 브리핑과의 연결

1. **수집 마감:** 브리핑 시각 T(D-5)보다 Δ분 앞에서 모든 활성 소스의 순방향 수집을 한 번 더 돌린다.
2. **스냅샷 고정:** `available_at ≤ T`인 자료 버전 목록과 `coverage`를 `briefing_snapshot_<T>`로 고정한다. 이후 들어온 자료·정정은 이 브리핑을 바꾸지 않는다.
3. **집계:** 스냅샷에서 종목·유형·주제별 건수, 공백 구간, 최신 자료 시각을 엔진이 계산한다.
4. **LLM 입력:** 현재 규칙(`AGENTS.md` §7)대로 **집계 수치만** 보낸다. 기사 제목·요약·출처 목록은 LLM에 보내지 않고 서버 템플릿이 따로 표시한다. 제목·요약을 LLM 입력으로 쓰려면 SRS·`AGENTS.md` 개정이 먼저다.
5. **발행 조건:** 필수 소스가 `gap`이면 "자료 부족"으로 발행하고 사유를 보인다. 휴장일 동작은 D-5.

## 11. 구체 실행 계획

주 단위(W)는 착수일 기준 상대 일정이다. 현재 제품의 4단계 통합·리허설(2026-10-18 ~ 10-21, [구현_계획 §0.2](../구현_계획.md))과 겹치지 않게 착수일을 정한다. **사용자** = 가입·키 발급·약관 판단처럼 사용자만 할 수 있는 일, **개발** = 코드·문서 작업(승인 후).

### 0단계 — 확인·결정 (W0, 3~5일, 코드 없음)

| # | 할 일 | 담당 | 산출물·판정 |
|---|---|---|---|
| 0-1 | **이용 목적 확정**: 비영리 연구·교육·시연인지, 상업 서비스인지 | 사용자 | 출처별 판정의 기준. 상업이면 RSS 대부분은 개별 허가 필요 |
| 0-2 | OpenDART 가입·인증키 발급 | 사용자 | 키는 채팅에 쓰지 않고 환경변수 `DART_API_KEY`로만 설정 |
| 0-3 | 네이버 개발자센터 애플리케이션 등록(검색 API) | 사용자 | Client ID·Secret 환경변수. 공식 문서에서 한도·`pubDate` 정의 직접 확인 |
| 0-4 | 빅카인즈 회원가입 후 **시험 다운로드**: 종목 1개(예: 삼성전자), 2021-01 ~ 2021-03 | 사용자 | 파일에 **시:분** 포함 여부, 건수 한도, 이용 조건(연구·상업), 대량·API 제공 문의 결과 |

**다음 단계로 넘어가는 조건:** 0-2와 0-6이 끝나면 1단계 착수. 뉴스(3단계)는 0-5에서 활성 피드가 1개 이상일 때.

### 1단계 — OpenDART 시험 측정 (W1 전반, 2~3일)

| # | 측정 | 판정 기준(제안) |
|---|---|---|
| 1-1 | 고유번호 ZIP으로 상장사 `corp_code`↔`stock_code` 매핑, 보유 종목 마스터와 매칭률 | 매칭률과 불일치 사례 목록 기록. 불일치는 상장폐지·코드 변경 여부로 분류 |
| 1-2 | 1개월 창(유가·코스닥)의 공시 건수·요청 수·소요 시간 → 5년 소급 요청 수 추정 | 5년 소급을 요청 제한 안에서 **며칠에 끝낼 수 있는지** 산출 |
| 1-3 | 순방향 폴링 1거래일 시험(5분 간격): 새 공시 발견 시각 기록, KIND 화면 시각과 20건 수기 대조 | 발견 지연(중앙값·최대) 기록 → §4 규칙 1의 보수성 확인 |
| 1-4 | 정정 공시 사례 10건의 보고서명·원공시 관계 확인 | 버전 연결 규칙 확정 |

측정 결과는 이 문서 §2.1·§4에 반영한다. 1-1 매칭률이 낮거나 1-3 지연이 커서 분봉 학습에 쓸 수 없으면 그 사실을 기록하고 공시는 일봉 학습 전용으로 둔다.

### 2단계 — OpenDART 본 구현 (W1 후반 ~ W3, 1.5~2.5인주)

1. 도메인: `timing`(§4 규칙), `dedup`(접수번호·정정 버전), 종목 연결 — 합성 데이터 단위 테스트 먼저.
2. 인프라: OpenDART 어댑터, 원본 보관(jsonl.gz), Parquet·SQLite 저장.
