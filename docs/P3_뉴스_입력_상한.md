# P3-8 뉴스 순방향 입력·네이버 실행 경로 — 검토용 초안

작성: hchee99 · 2026-10-07. 입력 기반은 PR #29, 실행 경로는 develop `44febaf` + #29 + 저장 복구 수정 #30 위에서 검증했다. G2 반영 전 병합·출처 활성화를 의미하지 않는다.

## 문제와 이번 동작

여러 종목 검색에서 같은 기사가 반복되고, 출처별 목록을 단순 병합하면 후속 처리량이 급증한다. 요청 계획·응답 파싱·관측 버전 생성·마감 시각 기준 중복 제거/선택을 순수 함수로 구현하고, 네이버 뉴스의 HTTP·요청 한도·저장·CLI를 연결했다. RSS는 응답 파서까지이며, 전체 운영 자동화나 기존 n8n 반영을 뜻하지 않는다.

합성 입력 4,532개의 서로 다른 기사와 50개의 출처 간 중복을 넣고 선택 상한 40을 적용하면, 선택 40·중복 50·보류 4,492를 반환한다. 보류는 데이터 없음이나 수집 완료로 바꾸지 않는다. 이는 건수 제한이며 토큰 한도 보장은 아니다. 이후 요약 단계는 입력 길이·토큰 한도를 별도로 검사해야 한다.

## 함수 계약

- `request_plan`: 명시된 질의 목록의 공백·중복을 정리하고 한 질의의 여러 페이지보다 다른 질의 첫 페이지를 우선한다. 실행당 상한과 남은 일 한도 중 작은 값을 사용한다. `next_cursor`로 다음 순번을 넘겨 낮은 상한에서도 뒤쪽 질의가 굶지 않게 한다. `remaining_daily`는 호출자가 잠금 아래 실제 잔여량을 계산해 주어야 한다. 계획만으로 동시 실행·재시도 한도가 강제되지는 않는다.
- `parse_naver`: 오류 응답·잘못된 페이지·모순되는 건수를 정상 빈 결과로 처리하지 않는다. 잘못된 항목은 원문을 오류에 노출하지 않고 개수와 `partial`로 남긴다. `more_results`가 있어도 과거 기간의 완전 수집을 주장하지 않는다.
- `parse_feed`: UTF-8 RSS 2.0·Atom을 받으며 바이트·항목 상한을 필수로 요구한다. DTD/entity를 거부하고 다른 사이트를 조회하지 않는다. 초과 항목 수와 `partial`을 반환한다. HTTP 수신 단계에서도 바이트 제한이 필요하다.
- `observe`: 제목은 텍스트로 바꾸고 원문 URL을 식별자로 삼는다. `utm_*`, `gclid`, `fbclid`, fragment만 제거하며 기사 번호·알 수 없는 질의 값·HTTP/HTTPS 차이를 보존한다. 출처별 `doc_id`와 출처 공통 `article_key`를 분리한다. 같은 제목만으로 다른 URL을 합치지 않는다.
- `normalize_poll`: 같은 조회 묶음에서 같은 URL·동일 내용은 한 번만 처리한다. 같은 URL의 서로 다른 내용은 순서를 단정하지 않고 충돌로 격리한다. 기존 이력은 변경하지 않고 새 버전만 반환한다. 오류/충돌이 있으면 완료 커서를 넘기지 않는 것은 저장 유스케이스의 책임이다.
- `select_cutoff`: `first_seen_at`과 `available_at` 모두 마감 시각 이하인 최신 버전만 선택하고 URL 중복을 제거한 뒤 상한을 적용한다. 미래 버전을 넣어도 과거 결과가 변하지 않는다. 과거 소급 모드는 지원하지 않는다.

## 출처·시각·권한

기본 출처는 비활성이며 `SourcePolicy.check()`가 비활성 출처를 거부한다. `metadata_only`이면 요약과 원문 참조는 비운다. `summary_link`는 별도 권한 확인 이후 호출자가 설정해야 한다. 어느 값도 LLM 전송 허가가 아니다. 종목 질의나 제목 일치만으로 종목 연결을 확정하지 않는다.

네이버의 `pubDate`는 `naver_provided`, 피드 게시 시각은 `feed_pubdate`로 구분한다. 출처 시각은 분석 가능 시각을 앞당기지 않는다. 첫 관측과 변경 버전은 수집기가 관측한 시각 이후에만 사용할 수 있다. 시간대 없는 값·거꾸로 간 관측 시계는 거부한다.

네이버 요청 형식과 페이지 범위는 [공식 뉴스 검색 문서](https://developers.naver.com/docs/serviceapi/search/news/news.md)를 2026-10-07 확인했다. 해당 문서는 검색 API 동작 근거이며 기사 재사용·재전송 허가의 근거가 아니다.

## 실행·저장 후속 구현

2026-10-07 후속 검증: 표준 ingest **134 passed / 5.73초**, engine **313 passed, 45 skipped / 249.94초**, api **30 passed, 53 skipped / 11.46초**. 뉴스 CLI의 비활성 실행과 가짜 HTTP를 통한 활성 실행→저장→상태 조회도 확인했다. 최신 develop의 추가 테스트와 원본 파일 부재로 이전 기록과 전체/skip 수가 다르며, 실데이터 회귀 통과를 주장하지 않는다.

- `regime-ingest run --source naver_news [--news-config <설정.yaml>]`는 기본 비활성이다. 비활성이면 키·HTTP·저장소에 접근하기 전에 `disabled`를 반환한다. 출처 대장/G2 검토 뒤 활성 설정과 `NAVER_CLIENT_ID`, `NAVER_CLIENT_SECRET` 환경변수를 사용한다. 키를 설정 YAML에 넣지 않는다.
- `regime-ingest status --source naver_news`는 질의 순번·KST 오늘 요청 수·최근 결과를 보여 준다. 자료를 새로 수집하지 않는다.
- 한도는 요청 직전 잠금 아래 SQLite에 예약·commit한다. 재시도·실패·중간 종료도 사용량에 남는다. 실행당 상한과 KST 일 한도를 모두 적용한다. 공유 네이버 계정의 다른 앱/API 사용량은 알 수 없으므로 이 수집기만의 로컬 예산이다.
- HTTP는 공식 뉴스 JSON 주소만 호출하고 인증값은 헤더에만 넣는다. 리디렉션을 따르지 않으며 응답 바이트 상한을 검사한다. 429/5xx/네트워크 오류는 제한된 횟수로 재시도한다. Retry-After가 허용 대기보다 크거나 해석 불가능하면 일찍 재호출하지 않고 중단한다. 서버 본문·예외 원문·키는 로그에 남기지 않는다.
- 뉴스 정책과 `article_key` 포함 스키마를 별도 manifest로 기록한다. 제목·링크만 허용하면 원본 JSON/description은 저장하지 않는다. 새 버전 Parquet·seen·커서·coverage·run을 확정한 후 임시 파일을 공개한다. commit 전 실패는 rollback, commit 후 rename 실패는 다음 출처 잠금에서 복구한다. #30은 다른 출처의 작업 중 파일을 정리하지 않는 수정이다.
- 응답 오류는 `gap`, 잘못된 행·상한으로 제한한 검색은 `partial`이다. 정상 검색도 `forward` 관측으로만 남기며 역사 기간의 완전 수집을 주장하지 않는다. 잘못된 행/충돌이 있으면 질의 커서를 넘기지 않는다. 검색 상한 때문에 일부 질의를 미룬 정상 응답은 순번을 넘겨 다음 실행에서 나머지를 조회한다.
- `select_cutoff`의 40건 선택 예시는 저장된 모든 정상 기사를 지우는 규칙이 아니다. 저장과 후속 브리핑 선택을 분리하며, LLM 입력 토큰 상한/허가는 별도다.

검증은 가짜 HTTP·합성 기사·임시 저장소를 사용했다. 실제 네이버 API·RSS·LLM 호출과 운영 n8n 변경은 하지 않았다.

운영 제한: 기존 Store의 출처 잠금은 파일 기반이다. 프로세스를 강제 종료해 잠금 파일이 남으면 다음 실행은 `skipped`로 멈추므로, 담당자가 이전 프로세스 종료를 확인한 후 잠금을 정리해야 한다. 시간 경과만으로 잠금을 자동 삭제하지 않는다. 이 작업의 자동 복구 검사는 잠금을 다시 획득할 수 있는 저장 실패·재실행에 대한 검사다.

남은 범위: G2/출처 대장 활성화, 조건부 RSS HTTP(ETag/Last-Modified/304), 스케줄·취소, n8n/브리핑 연결, 실제 소규모 운영 확인. 현재 CLI를 등록만 하면 전부 운영 완료라는 의미는 아니다.
