# 역방향 백테스트 설계 (P1)

목표 승률(예: 55% 이상)과 최소 거래 수를 입력하면, 정해진 탐색 범위 안에서 그 목표를 과거에 충족한 조건 조합을 찾는 기능이다. 후보마다 기존 백테스트 엔진을 그대로 돌리고, 탐색에 쓰지 않은 평가 구간에서 다시 확인한다.

- 담당: hongsungmin0315 · 관련 WBS: P1-1 ~ P1-11 · 결정: [구현_전_결정사항 §5.3 D-1](구현_전_결정사항.md)
- 근거: [SRS v2.0](SRS.md) §1.2·FR-A5·NFR-14(2026-10-01 승인), 팀 계획 [plan/01-presets-and-reverse-backtest.md](plan/01-presets-and-reverse-backtest.md). 이 문서는 그 계획의 D-1 세부 값과 계약을 정한다.

## 1. 현 계약 (P1-1.1, 2026-10-01 `develop` 7f9700f 기준)

### 1.1 전략 입력

엔진 `Strategy.from_dict`(구조 검증) → `Strategy.validate(cfg)`(값 검증). API는 `schemas.StrategyIn`(pydantic 엄격 모드, 알 수 없는 키 금지)이 1차 관문이다.

| 필드 | 타입·범위 | 생략 시 | 비고 |
|---|---|---|---|
| `name` | `^[A-Za-z0-9_\-]{1,64}$` | 필수 | 한 요청 안에서 중복 금지 |
| `patterns` | 핵심 5종 중 1개 이상, 중복 금지 | 필수 | `ma_cross_5_20`, `breakout_20d`, `breakout_vol`, `rsi_rebound`, `bb_lower_recover` |
| `combine` | `and` / `or` | `or` | |
| `exit.stop_loss_pct` | -50 ~ -1 또는 null | -8 | 퍼센트 단일 단위(-8 = -8%) |
| `exit.take_profit_pct` | 1 ~ 200 또는 null | 20 | |
| `exit.max_hold_days` | 정수 1 ~ 250 | 20 | |
| `exit.trailing_stop_pct` | null만 | null | |
| `markets` | KOSPI·KOSDAQ 부분집합 | 둘 다 | 진입 신호 필터(E1) |
| `period` | `{start, end}` YYYY-MM-DD, start ≥ 2020-09-01, end ≤ 기준일 | 전체 | 신호일 기준(E2) |
| `min_avg_value_krw` | 정수 ≥ 5억 원 | 5억 원 | |
| `cap_groups` | large·mid·small 부분집합 | 전체 | |

**패턴 수치(RSI 임계값, 거래량 배수 등)는 전략에서 바꿀 수 없다**(C-3, FR-P4). 값은 `engine/config/default.yaml`의 `patterns`에만 있다. 탐색 축에 패턴 수치를 넣으려면 P1-4(패턴 수치 파라미터화)가 먼저 필요하다.

### 1.2 실행·결과

| 계층 | 진입점 | 출력 |
|---|---|---|
| 엔진 | `runs.execute(strategies, prep, cfg, ctx)` | `{"strategies", "results": {이름: trades·skipped·summary·equity·cells_*}, "validation": DataFrame}`. 저장하지 않음 |
| 엔진 | `runs.run_and_save(...)` | `runs/<run_id>/` (meta.json, result.json, validation.parquet, universe.json, strategies/<이름>/*.parquet·summary.json). 임시 폴더에 쓴 뒤 완료 시 이동(E4) |
| API | `POST /runs` (202), `GET /runs`, `GET /runs/{id}`, `POST /runs/{id}/cancel`, `GET /runs/{id}/result` | 동시 실행 1개, 실행 중 요청은 `409 busy`(E4). 한 요청 최대 5전략(`MAX_STRATEGIES`) |

`summary` 지표 키: `trades`, `win_rate`, `mean_ret`, `median_ret`, `mean_hold_ret`, `mean_excess`, `payoff_ratio`, `sharpe`, `mdd`, `total_cost`, `excluded_trades`, `skipped_entries`, `skipped_by_reason`, `exit_by_reason`, `period_start`, `period_end`. 정의는 `backtest/metrics.py`의 `METRIC_DEFS`.

`validation` 열: `fdr_pass`(BH q ≤ 0.10, m = 요청 안 전략 수), `split_judgement`·`split_pass`(2024-02-29 전후), `random_percentile`·`random_pass`(무작위 1,000회 95 백분위), `analysis_target`(셋 다 통과).

### 1.3 승률 정의 (P1-1.2)

`win_rate` = 집계 포함 거래(`end_of_data` 제외) 중 **비용 차감 후 `net_ret > 0`** 인 거래의 비율.

- 손익 0은 승리가 아니다.
- 왕복 비용(0.30%)을 뺀 값 기준이라, 비용보다 작은 이익은 패배다.
- 거래가 없으면 NaN.

회귀 테스트 `engine/tests/test_win_rate.py`: 정의 경계 4건 + 합성 시장(30종목, seed 0)에서 핵심 5종의 거래 수·승률 고정값. 엔진·설정을 바꿔 이 값이 바뀌면 역방향 탐색 결과도 바뀌므로 의도한 변경인지 확인한다.

## 3. 탐색 범위 (P1-2, D-1 확정 2026-10-01)

### 3.1 입력

| 입력 | 규칙 | 생략 시 |
|---|---|---|
| 목표 승률 `target_win_rate` | 0 ~ 1 (0.55 = 55%). 판정은 기존 `win_rate` 정의 그대로 **이상**(§1.3) | 필수 |
| 최소 거래 수 `min_trades` | 정수 30 ~ 5,000 | 300 (`analysis.min_cell_trades`와 같은 기준) |
| 시장·시총 그룹·거래대금 하한 | 기존 전략 입력 규칙 그대로. 탐색 한 번에 값 1개(탐색 축 아님) | 기존 기본값 |
| 기간 `period` | 기존 규칙 + **분할일(2024-02-29)을 포함**해야 한다(start ≤ 분할일 < end) | 전체(2020-09-01 ~ 기준일) |

### 3.2 탐색 축

후보는 아래 축의 값 목록의 **곱집합**이다(전수 탐색). 무작위 표본·단계적 탐색은 쓰지 않는다.

| 축 | 허용 값 | 생략 시 |
|---|---|---|
| 패턴 | 핵심 5종 중 1~5개. 고른 패턴의 공집합 아닌 부분집합을 모두 만든다 | 5종 전체 |
| 결합 | `and`, `or`. 패턴 1개짜리 조합은 결합과 무관하므로 1개로 센다 | 둘 다 |
| 손절 % | -3, -5, -8, -10, -15, -20, null 중 선택 | [-8] |
| 익절 % | 5, 10, 15, 20, 30, 50, null 중 선택 | [20] |
| 최대 보유 거래일 | 3, 5, 10, 20, 40, 60 중 선택 | [20] |

- **패턴 수치(거래량 배수·RSI 문턱 등)는 이번 단계에서 열지 않는다.** 준비 프레임을 바꾸지 않는 축만 연다는 팀 계획의 첫 단계 안을 따른다. 패턴 수치 축은 P1-4(10/14~15)에서 조합별 패턴 수치 계약과 함께 추가한다.
- 허용 값을 이산 목록으로 둔 이유: 후보 수를 실행 전에 정확히 알 수 있고, 같은 요청은 항상 같은 후보(같은 순번)를 만든다(재현성).

### 3.3 후보 수·시간 상한 (NFR-14)

- 후보 수 = 패턴 조합 수 × 손절 수 × 익절 수 × 보유일 수. 패턴 5종·결합 2개면 조합 57개다.
- **상한 200개**(`search.max_candidates`). 넘으면 실행하지 않고 `422 too_many_candidates`로 후보 수와 상한을 알려 준다. 자동으로 줄이지 않는다.
- 예: 패턴 5종 × 기본 청산 = 57개. 패턴 3종·AND/OR(조합 3 + 4×2 = 11개) × 손절 3 × 익절 3 × 보유 2 = 198개.
- **예상 시간** = 후보 수 × `search.sec_per_candidate`(2.5초, §3.6 실측). 실행 전 미리보기에서 보여 준다. 상한 200개 × 2.5초 ≈ 8분.

### 3.4 구간 분할

신호일 기준으로 나누며, 분할일은 기존 기간 분할(FR-A3)의 `analysis.split_date`(2024-02-29)와 같다.

| 구간 | 기간 | 데이터 | 역할 |
|---|---|---|---|
| 탐색 구간 | 기간 시작 ~ 2024-02-29 | **2024-02-29까지만** 사용(as_of = 분할일) | 후보를 고른다 |
| 평가 구간 | 2024-03-01 ~ 기간 끝 | 전체 | 고른 후보를 처음 보는 기간에서 확인한다 |

탐색 구간 계산은 데이터를 분할일에서 잘라서 한다. 그래서 분할일 뒤 가격이 바뀌어도 탐색 결과와 후보 선택은 그대로다(테스트 `test_selection_ignores_evaluation_period_data`). 분할일에 보유 중인 거래는 기존 규칙대로 `end_of_data`(집계 제외)다. 지표·국면은 t일까지의 값만 쓰므로 자르기 전후 값이 같다(`test_lookahead` 절단 불변).

### 3.5 절차

1. **탐색**: 모든 후보를 탐색 구간에서 기존 엔진으로 실행해 요약 지표와 단측 p-value를 낸다. 패턴 신호는 패턴마다 한 번만 계산해 후보 간에 재사용한다. 무작위 벤치마크는 하지 않는다.
2. **평가**: 탐색 구간에서 **목표 승률 이상 + 최소 거래 수 이상**인 후보를 모두 평가 구간에서 다시 실행한다(무작위 벤치마크 1,000회 포함). 평가 구간 결과는 후보 선택에 쓰지 않는다.
3. **FDR**: 탐색·평가 두 구간 모두 BH(q = 0.10), **가족 크기 m = 시도한 전체 후보 수**. 평가하지 않은 후보는 p = 1로 두어 m에만 포함한다.
4. **상태**:

| 상태 | 조건 |
|---|---|
| `both` 탐색·평가 모두 충족 | 탐색 충족 + 평가 구간에서도 목표 승률 이상·최소 거래 수 이상 |
| `explore_only` 탐색만 충족 | 탐색 충족, 평가 구간에서 승률 또는 거래 수 미달 |
| `not_met` 미충족 | 탐색 거래 수는 충분하지만 승률 미달 |
| `insufficient_trades` 거래 수 부족 | 탐색 거래 수 < 최소 거래 수 |
| `not_evaluated` 평가 전 중단 | 탐색 충족 후보인데 평가 구간 재평가 전에 취소됨(취소된 탐색에만 나온다) |

5. **충족 후보가 없을 때**: 가장 가까운 후보(거래 수 충족 우선 → 승률 부족분이 작은 순 → 거래 수 많은 순)와 부족분(승률, 거래 수)을 돌려준다.
6. **정렬**: 상태(both → explore_only → not_evaluated → not_met → insufficient_trades) → 탐색 승률 내림차순 → 순번. 정렬 규칙을 결과에 함께 싣는다. "추천 순위"라는 표현은 쓰지 않는다.
7. **3중 검증 표시**: 기간 분할 = 탐색/평가 구간 분할 결과(상태), FDR = 두 구간 각각, 무작위 벤치마크 = 평가 구간.

**문구 원칙**: "목표 조건을 과거 구간에서 충족한 조합"으로만 표현하고, 표 위에 시도 후보 수와 "과거 결과이며 미래 성과를 보장하지 않습니다" 고지를 둔다.

## 4. 공개 계약 개정안 (P1-3)

원칙: **기존 계약(전략 입력, `POST /runs`, `runs/<run_id>/` 결과 폴더)은 바꾸지 않고 새 계약만 추가한다.** 그래서 기존 실행 결과와 화면은 그대로다(P1-11.2 기존 성과 불변).

### 4.1 전략 입력 (P1-3.1)

| 항목 | 개정 | 이유 |
|---|---|---|
| `Strategy` 필드 | **변경 없음** | 탐색 후보는 기존 필드(패턴·결합·청산·필터)로 표현된다. 후보를 그대로 `POST /runs`에 넣을 수 있다 |
| 패턴 수치 | 이번 개정에서 제외 | P1-4에서 `patterns` 원소를 `{"name", "params"}`로도 받는 하위 호환 확장을 따로 제안한다 |

새 입력 **탐색 요청(SearchRequest)**:

```json
{
  "name": "winrate55",
  "target_win_rate": 0.55,
  "min_trades": 300,
  "axes": {
    "patterns": ["breakout_20d", "rsi_rebound", "bb_lower_recover"],
    "combine": ["and", "or"],
    "stop_loss_pct": [-5, -8, null],
    "take_profit_pct": [10, 20],
    "max_hold_days": [10, 20]
  },
  "filters": {"markets": ["KOSPI", "KOSDAQ"], "min_avg_value_krw": 500000000, "cap_groups": ["large", "mid"],
              "period": {"start": "2020-09-01", "end": "2026-09-18"}}
}
```

검증 실패는 기존과 같은 `422 validation_failed`(`detail.fields`에 필드 경로). 후보 수 초과는 `422 too_many_candidates`(`detail = {candidates, max_candidates}`).

**후보 이름**: `c001`부터 순번. 순서는 패턴 조합(패턴 수 → 이름 사전순) → 결합(and, or) → 손절 → 익절 → 보유일(각 축의 허용 값 순서). 입력 순서와 관계없이 같은 요청이면 같은 순번이다.

### 4.2 API (P1-3.2)

| 메서드·경로 | 응답 | 비고 |
|---|---|---|
| `GET /searches/options` | `200` 축별 허용 값·기본값, 후보 상한, 최소 거래 수 범위, 분할일, 상태 목록 | 화면 입력용 (설정 `search:` 절) |
| `POST /searches/preview` | `200 {candidates, max_candidates, within_limit, estimated_sec}` | 실행하지 않고 후보 수·예상 시간만 계산. 상한을 넘어도 200(`within_limit = false`) |
| `POST /searches` | `202 {search_id, status, candidates, estimated_sec}` | |
| `GET /searches` | `200 {searches: [...]}` | 탐색 기록 목록, 최근 순 |
| `GET /searches/{id}` | `200` 상태 스냅샷 | `status`, `stage`, `stages`, `processed`, `total`, `met_so_far`, `elapsed_sec`, `error` |
| `POST /searches/{id}/cancel` | `202 {search_id, accepted}` | 다음 후보 경계에서 멈춘다 |
| `GET /searches/{id}/result` | `200` search.json + `status`, `disclaimer` | 완료 전이면 기존과 같은 `409 run_not_ready` 계열 |

- **작업 슬롯 공유**: 실행(`/runs`)과 탐색은 동시에 1개만 돈다(E4). 하나가 도는 중이면 `409 busy`, `detail = {kind: "run" | "search", id}`. 기존 `/runs`의 409 응답은 `detail.run_id`를 그대로 유지하고 `kind`만 추가한다(하위 호환).
- **진행**: 처리한 후보 수 / 전체 후보 수와 지금까지 목표를 충족한 수(`met_so_far`)만 보인다.
- **탐색 단계** (`stages`): `generate` → `explore`(탐색 구간 전 후보) → `evaluate`(평가 구간 재평가) → `save`.
- **취소**: 그때까지 처리한 후보를 `status = cancelled`(중단됨)로 기록에 남긴다. `counts.processed`가 처리한 후보 수, `fdr_family_size`는 그대로 시도하려던 전체 후보 수다. 결과 화면은 완료된 탐색처럼 보이지 않게 `cancelled`와 처리 수를 함께 표시한다. 예외로 실패하면 기록을 남기지 않는다(기존 실행과 같음).

### 5.1 저장 위치·범위

| 항목 | 결정 | 이유 |
|---|---|---|
| 위치 | `runs/presets/<preset_id>.json` (조합 1개 = 파일 1개) | `runs/`는 이미 Git 제외·로컬 결과 위치다. 경로 설정(`Paths`)을 늘리지 않는다 |

### 5.2 저장 형식

```json
{
  "format": 1,
  "id": "p_3f9a0c1d2e4b",
  "name": "RSI 반등 조합",
  "strategy": {"name": "p_3f9a0c1d2e4b", "patterns": [...], "combine": "or",
               "exit": {"stop_loss_pct": -5, "take_profit_pct": null, "max_hold_days": 10, "trailing_stop_pct": null},
               "markets": [...], "period": {"start": "2020-09-01", "end": "2026-09-18"},
               "min_avg_value_krw": 500000000, "cap_groups": [...]},
  "source": {"kind": "search", "search_id": "...", "candidate_id": "c004", "status": "both"},
  "data_as_of": "2026-09-18", "config_hash": "...",
  "created_at": "2026-10-02T09:00:01", "updated_at": "2026-10-02T09:00:01", "revision": 1
}
```

- **값 스냅샷(P1-9.3)**: `strategy`는 기본값을 모두 채운 값(`Strategy.effective`)이다. 설정 기본값이 나중에 바뀌어도 저장한 조합은 바뀌지 않는다. 그대로 `POST /runs`에 넣을 수 있다.
- 과거 실행 결과(`runs/<run_id>/meta.json`)와 탐색 기록은 실행 시점 값을 따로 담는다. 그래서 조합을 고치거나 지워도 과거 결과는 바뀌지 않는다.
- `name`: 자유 문자 1~60자(한글 가능), 앞뒤 공백 제거, 대소문자 무시 중복 금지. `strategy.name`은 실행 결과 표시용으로 `id`를 쓴다.
- `source.kind`: `search`(탐색 기록의 후보) 또는 `manual`(직접 작성). 탐색 후보를 저장할 때 기간은 탐색 구간이 아니라 **탐색 요청의 기간(없으면 전체)** 으로 저장한다. 기간은 탐색 축이 아니기 때문이다.
- P1-4(패턴 수치)가 들어오면 `strategy.patterns` 원소에 수치가 붙는다. `format`으로 구분한다.

## 7. 패턴 수치 파라미터화 (P1-4)

### 7.1 무엇을 열었나

| 패턴 | 수치 | 기본값 | 조합별 허용 범위 (`pattern_limits`) | 탐색 축 허용 값 (`search.pattern_axes`) |
|---|---|---|---|---|
| `breakout_vol` | `volume_mult` 거래량 배수 | 2.0 | 1.0 ~ 5.0 | 1.5, 2.0, 2.5, 3.0 |
| `rsi_rebound` | `threshold` RSI 문턱 | 30 | 10 ~ 50 | 20, 25, 30, 35, 40 |

- **준비 프레임에 들어가지 않는 수치만 연다.** 이동평균·돌파 참조 기간, RSI·볼린저 기간·배수는 준비 프레임 열(`sma5`, `high_max_prev20`, `rsi14`, `bb_lower` …)에 박혀 있어서, 바꾸면 준비 캐시가 무효가 되고 `PREP_VERSION`을 올려야 한다. 그래서 이번에는 열지 않는다(P1-4.2). **`PREP_VERSION` 변경 없음.**
- X6 후순위 패턴의 수치도 같은 방식으로 `pattern_limits`·`search.pattern_axes`에 항목을 더하면 열린다.

### 7.2 계약 (하위 호환)

- 전략 입력에 선택 필드 `pattern_params: {패턴: {수치: 값}}`를 더했다. 고른 패턴의, `pattern_limits`에 있는 수치만, 범위 안의 숫자만 받는다(오류 경로 `pattern_params.<패턴>.<수치>`).
- `pattern_params`가 없으면 `effective()`·`to_dict()`·결과·메타데이터가 기존과 **완전히 같다**(기존 성과 불변, `test_win_rate` 고정값 그대로).
- 있으면 실행 메타데이터의 전략에 조정 가능한 수치를 기본값까지 채워 기록한다. 이 값을 그대로 다시 넣어도 검증을 통과한다(조합 저장·불러오기 왕복).
- 탐색 요청 `axes.pattern_params: {패턴: {수치: [값...]}}`. 그 패턴이 든 조합에만 곱한다. 축이 없으면 후보 순번이 기존과 같다. 순서: 패턴 조합 → 결합 → 수치 조합(패턴 이름·수치 이름·허용 값 순) → 손절 → 익절 → 보유일.
- `GET /meta`의 `pattern_params`(기본값·최소·최대), `GET /searches/options`의 `pattern_axes`.

### 7.3 코드

- `patterns/base.py`: `Pattern(cfg, params)`가 설정 기본값 위에 조합별 수치를 덮어쓴다. `make_pattern(name, cfg, params)`, `compute_signals(..., params)`. `patterns/core.py`는 바꾸지 않았다(X6 작업 파일).
- `runs.py`: `Strategy.pattern_params` 검증·기록, `execute`가 신호 계산에 넘긴다.
- `search.py`: 수치 축 검증·곱집합, 신호 캐시 키 = (패턴, 수치).
- 화면: 빌더 패턴 카드 아래 "세부 조건"(기본값과 다른 값만 전송), 탐색 화면 수치 축 칩, 결과·저장 목록 조합 설명에 바꾼 수치 표시.

### 7.4 테스트 (`engine/tests/test_pattern_params.py`, `api/tests/test_search_contract.py`)

검증 경계 8건, 기록·왕복, 문턱별 신호가 정의와 일치, **절단 불변**(수치 2종 × 절단점 3개, P1-4.3), 기본값을 명시해도 결과 동일, 수치를 바꾸면 결과가 바뀜, 탐색 축 곱집합·순번·검증, 조합 저장 보존, API 계약 4건.
